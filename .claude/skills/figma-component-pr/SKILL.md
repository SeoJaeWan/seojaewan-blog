# 피그마 컴포넌트 PR 처리

입력: `feat/figma-<컴포넌트>` PR 번호.

이 스킬은 절차만 담는다. 규칙은 아래 `@codocs \[[문서:섹션]]` 링크가 가리키는 섹션에 있고, 실행할 때 codocs MCP의 `codocs_get`으로 그 섹션을 읽어 따른다. 규칙을 이 파일에 옮겨 적지 않는다.

이 스킬이 따르는 섹션: @codocs [[디자인 시스템:스킬]]

## 하지 않는 것

- @codocs [[디자인 시스템:스킬]]에 적힌 하지 않는 것(피그마에서 온 자료 고치기, 생성 파일 손으로 고치기, 병합)과 멈추는 경우를 따른다.
- 컴포넌트를 손으로 구현하거나 동작을 스킨에 잇지 않는다. 스킨·스토리와, 스킨에 동작을 합친 컴포넌트는 CI의 생성기가 만든다(@codocs [[디자인 시스템:세 겹]], @codocs [[디자인 시스템:동작의 종류]]).
- 생성 스크립트 고치기. 생성이 안 되거나 결과가 틀리면 멈추고 보고한다.
- `.codocs` 고치기. 고쳐야 하면 무엇을 왜 바꿀지 사용자에게 제안하고 멈춘다(@codocs [[개발 컨벤션:작업 원칙]]).

## 절차

1. 문서를 읽는다.
   - @codocs [[디자인 시스템:PR 흐름]], @codocs [[디자인 시스템:CI]]
   - @codocs [[디자인 시스템:세 겹]], @codocs [[디자인 시스템:동작의 종류]]
   - @codocs [[디자인 시스템:스키마]], @codocs [[디자인 시스템:생성 결과 검증]], @codocs [[디자인 시스템:스토리 규칙]]
   - @codocs [[디자인 시스템:아이콘 자리]], @codocs [[디자인 시스템:자산]], @codocs [[디자인 시스템:토큰 생성]]
   - @codocs [[디자인 시스템:조립]]
   - @codocs [[Git 작업 규칙:Changesets]]
2. PR 브랜치를 받는다(`gh pr checkout <번호>`). `main` 대비 바뀐 파일이 @codocs [[디자인 시스템:피그마 플러그인]]에서 컴포넌트 PR이 바꾸는 파일(그 컴포넌트의 스키마와 검증 자료)과 changeset, CI가 생성해 커밋한 생성 파일뿐인지 확인한다. 예상 밖 파일이 있으면 멈추고 보고한다.
3. 구현 자료를 순서대로 본다(@codocs [[디자인 시스템:스킬]]): 내보낸 스키마와 CI의 검증 결과 → `.codocs`(동작·코드·접근성) → 그래도 모르는 것만 피그마 MCP. 스키마와 MCP가 다르면 스키마를 따르고, 차이와 MCP로 메운 것을 보고한다.
4. 스키마의 동작 종류가 등록부(`packages/design-system/src/behaviors/`의 동작 등록부)에 있는지 본다. 없으면 멈추고 보고한다. 새 종류는 그 종류를 쓰는 컴포넌트를 내보내기 전에 먼저 만들어 `main`에 넣어야 하므로(@codocs [[디자인 시스템:동작의 종류]]), 이 PR에서 만들지 않고 종류를 `main`에 넣은 뒤 이 PR의 생성을 다시 돌려야 한다고 보고한다. 쓰는 토큰이나 자산이 코드에 없으면 같은 방식으로 멈추고, 토큰 PR·자산 PR을 먼저 병합한 뒤 이 PR에 `main`을 받아 와야 한다고 보고한다(@codocs [[디자인 시스템:PR 흐름]]).
5. CI가 그 PR에 생성 파일을 커밋했는지, 검증 결과가 통과했는지 `gh pr checks <번호>`와 PR 커밋으로 본다. 생성이 아직 돌지 않았거나 실패했거나 검증이 실패했으면 멈추고 어느 레이어의 어느 값이 다른지 보고한다. 생성 파일이 들어왔으면 받아 온다(`git pull`). 생성된 스킨·스토리·합친 컴포넌트가 @codocs [[디자인 시스템:스키마]]의 파일 자리에 있는지 본다.
6. 옛 컴포넌트와 옛 내보내기 자료를 지운다. 새 컴포넌트와 같은 자리의 손으로 쓴 옛 코드(옛 구현, 옛 스토리, 옛 테스트), 그 컴포넌트의 옛 내보내기 자료(`packages/design-system/figma/components/<이름>/`), 그 컴포넌트가 받던 옛 모션 자료와 `motion.css`의 그 클래스(`packages/design-system/figma/motions/`)를 지운다. 새 컴포넌트가 움직임을 `Motion` 변형으로 받는 경우다(@codocs [[디자인 시스템:생성 결과 검증]]). 생성 파일과 피그마에서 온 새 자료는 지우지 않는다.
7. 앱과 이 컴포넌트를 품은 옛 컴포넌트가 새 컴포넌트를 쓰도록 고친다.
   - 옛 컴포넌트를 import하는 곳을 모두 찾아 새 컴포넌트로 바꾼다. 입력의 이름과 값은 @codocs [[디자인 시스템:컴포넌트 입력]]을 따른다.
   - 이 컴포넌트를 품은 옛 컴포넌트는 안쪽에서 새 컴포넌트를 쓰게 한다.
   - 아이콘 자리는 필수 입력이라 쓰는 곳이 빠뜨리지 않고 넘긴다(@codocs [[디자인 시스템:아이콘 자리]]).
   - 놓인 자리에 따라 다른 동작의 종류가 필요하면 조립이 스킨에 직접 잇는다(@codocs [[디자인 시스템:동작의 종류]], @codocs [[디자인 시스템:조립]]).
   - 값은 토큰 클래스로만 쓴다(@codocs [[디자인 시스템:토큰 생성]]의 이름 규칙).
   - 새 컴포넌트로 모습을 맞추려고 생성 파일을 고치지 않는다. 안 맞으면 멈추고 보고한다.
8. changeset을 맞춘다(@codocs [[디자인 시스템:PR 흐름]]의 changeset, @codocs [[Git 작업 규칙:Changesets]]). 플러그인이 올린 changeset(`@seojaewan/design-system`, `patch`)은 그대로 두고, 앱을 고쳤으면 앱(`apps/web`)을 더하거나, 쓰는 방법이 바뀌었으면 종류를 올린다.
9. 푸시한 뒤 CI의 결과(생성 결과 검증을 포함한 `pnpm test`)는 PR 체크에서 본다. 로컬 확인은 두지 않는다(@codocs [[디자인 시스템:스킬]]). 코드를 고치다 생긴 모르는 클래스나 타입 오류를 찾는 데는 `pnpm lint`와 `pnpm typecheck`를 쓸 수 있다.
10. 커밋하고 푸시한다. 커밋 규칙은 @codocs [[Git 작업 규칙:커밋]]을 따른다. PR 브랜치에 이어서 커밋하고 병합하지 않는다.
11. 보고한다.
    - 확인한 CI 생성·검증 결과, 스키마와 MCP가 달라 스키마를 따른 곳과 MCP로 메운 것
    - 지운 옛 컴포넌트와 옛 내보내기 자료, 고친 앱·옛 컴포넌트의 쓰는 곳, changeset
    - 사람이 모습을 봐야 할 곳: 검증이 견주지 않는 글자의 획 모양, 자산 안쪽 그림, 재질의 흐림(@codocs [[디자인 시스템:재질 구현]]), 앱에서 이 컴포넌트가 놓인 자리
