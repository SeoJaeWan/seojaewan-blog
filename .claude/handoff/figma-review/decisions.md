# Screens 검토에서 정한 것 (2026-11-26, 아직 문서·피그마 반영 전)

## 큰 방향

- 디자인 시스템 = 한 번 내린 디자인 결정을 디자인과 코드가 같은 이름으로 다시 쓰게 하는 약속.
- 조립과 화면의 틀도 Windows 스타일 디자인 시스템에 속한다. 블로그는 채워 넣는 내용.
- 조립은 디자인 시스템 패키지에 Compound 꼴(Root/부분)로 둔다. 사람이 쓴다(생성 아님). 스토어·데이터·주소를 가져오지 않는다.
- 조립이 디자인 시스템에 오면 장면의 움직임(타이밍, stagger)도 조립이 갖는다.
- 검토 방식: 브라우저 창의 피그마를 같이 보며 Screens를 하나씩. 순서: 바탕화면, 작업 표시줄, Start, 검색, 탐색기, Chrome, 창, 다시 시작.

## 1-1 바탕화면 기본 (93:297)

- Taskbar와 Desktop은 나눈다(서로 모름). 한 화면에 놓는 일은 바깥(셸 뿌리).
- Desktop = 배경화면 + 아이콘 격자. 이것이 조립. 아이콘(DesktopFileItem)은 격자에 넣기만 한다.
- Taskbar는 위에 겹쳐 놓는다(absolute). 격자는 아래를 작업 표시줄 높이(48)만큼 비운다. 값은 밖에서 받지 않고 같은 크기 값을 쓴다.
- 격자: 칸 76x74, 바깥 여백 8, 사이 세로 16, 가로도 16(사용자 결정).
- 피그마: 좌표 프레임 icons를 격자 슬롯으로 바꾸고 배경과 묶어 Desktop 컴포넌트로 만든다(아직 안 함).

## 1-2 바탕화면 우클릭 메뉴 (3432:12988)

- 우클릭 메뉴는 <Desktop> 안에 둔다. 빈 곳 우클릭 시 뜬다(사용자 결정).
- 보기 크기(큰/보통/작은 = DesktopFileItem Size), 자동 정렬, 정렬 기준은 Desktop의 상태. 앱이 알아야 하는 항목(새로 만들기 등)만 사건으로 알린다.
- 고칠 것: Patterns의 Menu/Desktop, Menu/ViewSubmenu 안 separator가 아직 프레임(MenuSeparator로 교체). Patterns의 다른 메뉴도 확인.
- 격자 칸 크기는 Size 셋마다 필요(지금 아는 것은 Medium 76x74뿐).
- (고침, 사용자 결정) 우클릭 메뉴는 Desktop이 내용까지 갖는 것이 아니다. <Desktop> 안에 <ContextPanel>을 부분으로 넣고, 앱이 그 안에 항목과 이벤트를 넣는다. 우클릭을 받는 요소도 고른다(Base UI의 Trigger 방식). 보기 크기 등은 Desktop의 입력이 되고 상태는 앱이 갖는다.
- (사용자 결정) 칸 크기·자동 정렬·정렬 기준의 상태와 바꾸는 법은 Desktop이 갖고, 손잡이(useDesktop 같은 것)를 연다. 앱은 메뉴 항목을 놓고 손잡이를 꽂는다. 값을 넘기면 앱이 대신 갖는다(controlled/uncontrolled).
- 공통 규칙(사용자 동의): 조립은 자기 상태를 스스로 갖고, 읽고 바꾸는 손잡이를 연다. 앱은 손잡이를 꽂거나 값을 직접 넘겨 대신 갖는다.

## 1-3 바탕화면 끌어서 선택 (3888:16980)

- (사용자 결정) 끌어서 선택은 Desktop이 한다. 상자(SelectionMarquee)를 그리고 걸린 아이콘을 Selected로 만든다. 앱은 손잡이로 선택된 것을 읽는다.
- 피그마: SelectionMarquee(3888:17031)를 화면 위가 아니라 격자 안의 것으로.
- 구현 세부(내가 정함): 선택 로직은 한 번 만들어 Desktop과 탐색기가 함께 쓴다.

## "조립"의 뜻 (사용자 결정)

- 조립 = <Desktop> 같은, 디자인 시스템이 주는 이름 있는 그릇. 틀·부품 사이 규칙·상태와 손잡이를 갖고 자식으로 부품을 받는다.
- 층: 부품 / 조립 / 앱(조립 안을 채우고 이벤트에 답함). 앱에는 조립이 남지 않는다.
- 피그마 Patterns의 조립과 코드의 조립이 같은 이름.
- Desktop: 작업 표시줄을 뺀 바탕화면 전체가 조립 하나. 배경+격자 한 몸, 아이콘은 바로 자식으로. Root/Icons로 나누지 않는다.
- 피그마: Patterns Desktop/Scene에서 Taskbar/Default를 빼고 icons를 격자 슬롯으로. Screens 17장은 Desktop과 Taskbar를 나란히 놓게 바꾼다.
- 미정: 아이콘이 어느 칸에 있는지 누가 갖나(내 의견: Desktop).
- (사용자 결정) 아이콘이 어느 칸에 있는지는 Desktop이 갖는다. 앱이 값을 넘기면 앱이 대신 갖는다.
- (내가 정함) 아이콘은 DesktopFileItem을 감싸지 않고 그대로 자식으로 넣는다. Desktop이 자리를 기억하려면 아이콘마다 id가 필요하다.

## 기능을 나타내는 법 (사용자 결정, 앞의 안들을 대신함)

- 틀린 안들: (1) 메뉴를 Screens 내용 견본으로 옮기기 (2) Desktop.ViewMenu 같은 통 (3) 기능 표를 문서에.
- 메뉴는 통으로 주지 않는다. 블록(Menu, MenuItem 변형들, MenuSeparator)이 부품이고, 조립에 "우클릭했을 때의 모습"을 블록으로 엮어 둔다. Patterns의 Menu/Desktop, Menu/ViewSubmenu 통은 없앤다.
- 조립의 기능은 피그마의 흐름(프로토타입)으로 나타낸다. 기본 Desktop 하나에서 끌기·우클릭·선택으로 가는 흐름, 메뉴에서 "보기"에 올렸을 때, 항목을 눌렀을 때의 흐름. 모습 = 네모, 기능 = 화살표.
- 확인: Patterns에 이미 NAVIGATE 72, ON_DRAG 1, ON_KEY_DOWN 10. 피그마 계기에 우클릭 없음(ON_CLICK/ON_HOVER/ON_PRESS/ON_DRAG/AFTER_TIMEOUT/MOUSE_ENTER·LEAVE/ON_KEY_DOWN) → 대신 걸 방법 정해야 함.
- 한계: 흐름은 예시. "어떤 경우든"의 규칙만 문서에 남긴다.
- 화살표의 전환 시간·이징이 장면 움직임의 자리.
- 부품은 독립(어디에 놓이는지 모름). 부품 = 자기 모양·자기 상태·자기 안에서 끝나는 동작. 조립 = 부품 사이의 관계와 기능.

## 2. Taskbar (2-1 화면 98:6321)

- (사용자 결정) Taskbar는 영역을 나눈 그릇이다: Left / Center / Right. 그 안에 요소(시작 버튼, 검색, 앱 버튼, 시계)를 넣는다. 시작·검색·시계를 Taskbar가 굳혀 갖는다는 내 안은 버림.
- 피그마: Shell의 Taskbar는 이미 슬롯 Center, Right + 프레임 "left space". left space를 Left 슬롯으로. Patterns의 Taskbar/Default(통)는 없애고 기본 내용·흐름 장면으로.
- Taskbar가 갖는 것: 띠의 모양·높이 48, 가운데 영역이 늘 화면 가운데, 영역 사이 규칙.
- 미정: 미리보기(앱 버튼에 올리면 뜨는 것), 다른 조립으로 넘어가는 흐름(시작 버튼 → Start), 창과의 관계.
- (사용자: "나쁘지 않네") 미리보기는 Taskbar.App이 버튼과 Taskbar.Preview를 짝짓는다. 뜨는 지연, 한 번에 하나, 옆으로 옮기면 바로 바뀜, 버튼 위 가운데는 Taskbar가 갖고, 어떤 창이 들어가는지는 앱. 피그마에는 "앱 버튼에 올리기 → 미리보기 열림" 흐름.

## Desktop 시험 제작에서 정한 세부 (2026-11-26, 포크가 만듦. 노드 id는 figma-state.json)

- 격자: 슬롯에는 GRID를 쓸 수 없다(피그마가 막음). Icons 슬롯을 세로 자동 레이아웃 + 줄바꿈(WRAP)으로 만들었다. 위에서 아래로 채우고 넘치면 오른쪽 줄. 사이는 spacing/lg(16), 여백은 spacing/sm(8) 변수(기존 icons 프레임이 쓰던 것). "어느 칸에든 놓기"는 나타내지 못한다.
- 기존 Desktop/Scene의 icons는 좌표가 아니라 이미 세로 자동 레이아웃(사이 16, 여백 8, 변수 묶임)이었다. 앞서 "좌표로 놓았다"고 한 것은 틀림.
- 칸 크기: Large 112x122, Medium 76x74, Small 76x58 (DesktopFileItem 크기 그대로).
- 변형 축: State(Rest/Selected/Selecting/Menu/Menu view) x Icon size(Large/Medium/Small). Rest만 크기 셋, 나머지는 Medium만(7개).
- 선택 상자는 슬롯이 아닌 레이어 Selection(Selecting 변형에만 있음)에 SelectionMarquee. Desktop이 스스로 그리는 것이라 슬롯으로 두지 않았다.
- 우클릭: 피그마 계기에 우클릭이 없어 이름이 hit/우클릭인 투명 레이어에 ON_CLICK. 레이어 이름이 계기의 뜻. 버린 것: ON_KEY_DOWN 93(키보드 메뉴 키만 뜻함), ON_PRESS(떼면 되돌아감), 변형 이름으로만 뜻하기.
- 슬롯에는 상호작용을 걸 수 없다. 끌기는 hit/끌기 레이어(안에 hit/우클릭)에 ON_DRAG. ON_DRAG는 전환이 없으면 거부되어 SMART_ANIMATE LINEAR 83ms(기존 상태 전환 값).
- 메뉴가 뜨는 움직임: 화살표는 즉시 전환, Menu 변형 안의 Menu 인스턴스를 Motion=Enter Down으로 두어 나타냄. 하위 메뉴는 Motion=None.
- "보기" 열린 모습: MenuItem Variant=Submenu, State=Open(3975:791)은 Label·Icon 속성이 먹지 않아(글자 "메뉴 항목"으로 남음) Hover 변형을 썼다. Open 변형은 고쳐야 한다(기존 노드라 손대지 않음).
- 걸지 않은 화살표: Selecting을 놓았을 때(둘 선택된 모습의 변형이 없음), Rest·Large/Small에서 우클릭(Menu 변형이 Medium뿐), 자동 정렬 토글·정렬 기준·새로 만들기(도착 모습 없음).
- 컴포넌트를 복제하면 슬롯이 일반 프레임이 된다. componentPropertyReferences.slotContentId로 다시 이어야 한다.
- 섹션을 흐름도 꼴로 다시 놓음: 화살표는 reactions를 읽어 그린다(review/draw-flow-arrows.js, 다시 돌리면 flow arrows 레이어를 지우고 새로 그림). 기본에서 멀어지는 것만 선, 되돌아가는 것은 각 모습 아래 글줄.
- 하위 메뉴 자리: [[디자인 시스템:팝업]]의 간격 spacing/xs(4)와 right-start, 코드 menu-popup.tsx(SubmenuRoot, side inline-end, align start)대로 연 항목 오른쪽에 위를 맞춰 놓음. 기존 화면 1-2는 하위 메뉴가 (1206,419)로 어긋나 있음(고치지 않음).
- 문서와 다른 점(미정): [[디자인 시스템:팝업]]은 팝업이 열리는 흐름을 "Open overlay로 Menu/... 조립을 띄운다"고 적는다. 시험 제작은 Desktop 변형 사이 CHANGE_TO로 걸었다. 또 하위 메뉴는 400ms 머물면 연다고 적혀 있는데 '보기'의 마우스 들어옴에 지연을 넣지 않았다.

## Desktop 흐름도 2차 (가로 배치, 빠진 기능 더함)

- 규칙(코디네이터 전달): 조립의 기능은 저마다 화살표를 적어도 하나 갖는다. 필요한 모습은 더 만든다. 모든 조합이 아니라 대표 길 하나만. 정확하지 않은 화살표는 걸지 않는다.
- 흐름도는 가로 나무: 열 = 기본에서의 깊이, 행 = 같은 부모 아래 순서. review/draw-flow-arrows.js가 reactions를 읽어 자리와 화살표를 함께 정한다(모습이 늘면 다시 돌리면 됨). 열 사이는 화살표 글자 폭을 재서 정한다.
- 변형 축 Auto arrange=On/Off 추가. 새 모습: 여러 아이콘 선택됨, 자동 정렬 꺼짐, 아이콘을 옮김, 메뉴 열림(꺼짐), '보기' 하위 메뉴(꺼짐), '정렬 기준' 하위 메뉴, '새로 만들기' 하위 메뉴. 변형 14, 흐름 30.
- 놓기 계기: MOUSE_UP(typings에 있음, 걸림). Selecting의 Selection 레이어에 걸었다.
- 슬롯 안 자유 배치: 됨. 자동 레이아웃 슬롯의 자식을 절대 위치(layoutPositioning=ABSOLUTE)로 두면 칸 좌표(x=8+열*92, y=8+행*90)에 놓을 수 있다. 다만 하나만 절대로 빼면 나머지가 당겨 올라와, 옮긴 모습에서는 아이콘 넷을 모두 절대 위치로 뒀다.
- 두 걸음을 화살표 하나로 잇지 않았다. "빈 곳 우클릭 → 보기"를 한 화살표로 걸면 프로토타입에서 한 번 누르기에 하위 메뉴까지 열려 틀리다. 메뉴 열림(꺼짐)을 따로 만들어 한 걸음씩 걸었다.
- 자동 정렬 꺼짐(옮기기 전)에는 우클릭·선택 화살표를 걸지 않았다(도착 모습이 켜짐 쪽이라 틀림).
- 정렬 기준·새로 만들기: 내용은 [[바탕화면 우클릭 메뉴:빈 곳]]과 앱 코드에 정해져 있다(이름·항목 유형·수정한 날짜, 기본 이름 / 폴더). 하위 메뉴가 열리는 모습까지만 그렸다. 항목을 누른 뒤는 걸지 않음: 정렬은 결과 순서를 그림으로 확정하지 못했고(비교 규칙을 견본 아이콘에 대어 보지 않음), 새 폴더는 어느 칸에 어떤 상태(이름 바꾸기)로 생기는지 문서에서 찾지 못함.
- 붙여넣기(단추 줄)는 그리지 않았다(문서에는 있음).
- 복제한 변형에서 딸려 온 흐름: 복제 직후 지우기가 안쪽 인스턴스 항목에는 먹지 않아, 변형을 다 만든 뒤 한 번 더 지워야 했다.

## hit 레이어를 없애고 설명으로 (사용자 결정)

- 변형 안에는 화면에 실제로 있는 것만 둔다. hit/… 투명 레이어는 모두 지웠다(13개).
- 실제 레이어가 없는 흐름(빈 곳에서 끌기, 빈 곳 우클릭, 빈 곳 누르기, 밖 누르기)은 컴포넌트 세트 설명의 `흐름:` 아래에 한 줄에 하나씩 적는다: `<출발 모습> · <무엇을 하면> → <도착 모습>`. 모습 이름은 흐름도 이름표와 같은 말.
- 실제 레이어에 걸 수 있는 흐름(아이콘 누르기, 메뉴 항목, Esc, 놓기, 아이콘 끌어 옮기기)은 진짜 상호작용.
- 변형 뿌리에 걸기: 된다. 뿌리에 ON_CLICK·ON_DRAG를 걸면 자식에 걸린 것이 먼저 잡히고 나머지가 뿌리로 온다(피그마 규칙. 실제로 돌려 보지는 않음). 한 뿌리에 같은 계기 둘이 필요한 경우는 이번에 없었다. "무엇을 하면"의 말은 설명 줄에서 온다(뿌리의 누르기가 우클릭인지 그냥 누르기인지는 계기만으로 알 수 없음).
- 뿌리에 건 누르기의 한계: 메뉴가 열린 모습에서 흐름이 안 걸린 항목을 눌러도 뿌리가 받아 메뉴가 닫힌다.
- draw-flow-arrows.js: 상호작용과 설명 줄을 합친다. 뿌리의 누르기·끌기는 같은 (출발, 도착)의 설명 줄과 짝지어 그 글자를 쓰고, 설명 줄에만 있는 흐름도 그린다. 설명 줄의 모습 이름이 이름표 표에 없으면 오류. 짝 없는 뿌리 흐름은 unnamedRootReactions로 알린다. 피그마는 설명을 읽을 때 작은따옴표를 &#39;로 돌려준다(스크립트가 되돌림).

## 새 폴더와 정렬 기준의 "누른 뒤" 줄기 (사용자 승인)

- 줄기: '새로 만들기' 하위 메뉴 —'폴더' 누르기→ 새 폴더 이름 바꾸는 중 —Enter→ 새 폴더 생김 —빈 곳 우클릭→ 메뉴 열림 (새 폴더) —'정렬 기준'에 올리기→ '정렬 기준' 하위 메뉴 (새 폴더) —'수정한 날짜' 누르기→ 날짜순으로 정렬됨.
- 변형 축 New folder(No/Yes), Sort by(Name/Modified) 추가. 변형 19, 흐름 36.
- 확인한 규칙: 이름순 = 휴지통, Blog, 새 폴더, GitHub, 이력서. 날짜순 = 휴지통, 새 폴더, Blog, GitHub, 이력서([[항목 정렬:비교 규칙]]). 새 폴더는 만들자마자 고르고 이름 바꾸기 시작(desktop-icons-layer.tsx createFolder → selectOnly, startRename). 바탕화면 아이콘은 이름 바꾸는 동안 선택 바탕 없이 입력창만([[항목과 폴더:폴더 이름]]) → DesktopFileItem State=Rename.
- 지시와 달랐던 곳: (1) Enter로 확정한 뒤의 상태는 문서에 없다. 코드(use-folder-rename.ts)는 선택을 유지하고 키보드 포커스를 항목에 돌려준다. 피그마에 "선택됨+포커스" 변형이 없어 Selected로 그렸다. (2) 빈 곳 우클릭은 선택을 지운다([[항목 조작]] 표). 그래서 메뉴 열림 (새 폴더)에서는 새 폴더가 선택돼 있지 않고, 메뉴를 닫으면 돌아갈 "선택 안 된 새 폴더" 모습이 필요해 `새 폴더 있음`(Rest, New folder=Yes)을 하나 더 만들었다.
- 이름 바꾸는 중 Esc: 문서에 없어 걸지 않았다(코드에는 Esc=취소, 바깥 누르기=확정이 있다).
- 기본 쪽 '정렬 기준' 하위 메뉴는 없앴다. 눌러도 달라지는 것이 없는 모습이고, 화살표가 없는 것은 틀린 화살표가 아니라고 봤다. 그 결과 "메뉴 열림"에서 '정렬 기준'에 올리는 흐름은 그려져 있지 않다.
- DesktopFileItem의 State=Rename 변형은 Name 속성이 입력 글자로 가지 않는다(안쪽 RenameField의 Text 속성이 따로, 기본값 "파일 이름"). 인스턴스에서 안쪽 속성을 '새 폴더'로 덮었다. 기존 컴포넌트는 고치지 않음.
- 스크립트: 같은 (출발, 도착)의 앞으로 가는 흐름이 여럿이면 화살표 하나에 글자를 이어 적는다(메뉴 열림 (새 폴더) —Esc · 밖 누르기→ 새 폴더 있음). Enter(키 13)를 읽는다. 이름표 표의 키는 축 다섯 개 값.

## Shell (사용자: "나쁘지 않네")

- Shell도 조립 하나다. 안에 조립(Desktop, Taskbar, Start, 검색, 창)을 넣는다. 조립 사이의 흐름(시작 버튼 → Start 등)은 Shell의 흐름도다.
- Shell의 흐름도는 다른 조립과 같은 자리(Patterns)에 같은 꼴로 둔다(Screens에 그리자던 내 안은 고침). Screens는 Shell의 모습을 화면 크기별로 늘어놓은 곳으로 남는다.
- Shell이 갖는 것: Desktop 위에 Taskbar 겹침, 지금 열린 것(Start/검색/없음), 하나가 열리면 다른 것이 닫힘.
- 부품 페이지 이름 Shell과 조립 Shell의 이름이 겹침 → 정해야 함.
- Taskbar의 흐름도에는 Taskbar 안에서 끝나는 것만(미리보기, 버튼 표시).

## Taskbar와 창, 기본 제공 (사용자 의견)

- 창의 상태는 Shell이 갖는다. Taskbar의 버튼에는 Shell의 손잡이를 꽂는다(Desktop의 MenuItem ↔ useDesktop과 같은 방식).
- 공통 규칙(사용자 제안): 블록으로 직접 만들 수 있게 하고, 자주 쓰는 엮음은 기본 제공으로도 준다. 예: ExplorerButton, ChromeButton(아이콘·이름·Shell 연결이 끝난 것) + 사용자가 TaskbarButton으로 자기 버튼을 만들 수 있음. 앱 코드에 'explorer' 같은 문자열이 박히지 않게.
- 기본 제공은 블록과 손잡이만으로 만들어져 있어야 한다(숨은 능력 없음) — 내가 덧붙인 조건.
- 피그마에서는 조립의 슬롯 기본 내용이 곧 기본 제공의 모습.
- 구현 세부는 지금 정하지 않는다(사용자: "구현의 이야기라 지금 하는 게 맞나").

## Start·검색 (사용자 결정: "좋아 따로 두자")

- Start와 검색은 각각 조립으로 두고 자기 흐름도를 갖는다. Taskbar 흐름도에는 여닫기만. Taskbar의 Panel area 슬롯에 Start/검색 조립이 들어간다.
- 흐름은 다 그린다(보기 바꾸기, 타일 옮기기·우클릭, 글자 목록, 범주 폴더, 전원 메뉴, 검색 입력 전/후 등). 문서대로.

- Taskbar 앱 버튼 우클릭 메뉴도 Taskbar 흐름도에 넣는다(사용자 요청).

## Desktop 화살표 레이어가 밀린 사고 (2026-11-26)

- 증상(코디네이터 전달): Desktop의 flow arrows(6029:9504)가 아래로 10,572 밀려 Taskbar 섹션 위에 겹침. 코디네이터가 (0,0)으로 되돌림.
- 원인은 찾지 못했다. 확인한 것: (1) 새 폴더 줄기를 그린 뒤 찍은 Desktop 캡처에서는 제자리였다. (2) 그 뒤 내 호출 가운데 Desktop 섹션의 노드를 쓰기로 건드린 것은 없다(Taskbar 호출은 Desktop의 글자 노드를 복제하고 기본 변형의 인스턴스를 만들었을 뿐). (3) 10,572 = 표 높이 10,560 + 간격 12로, 세로 자동 배치인 item/Desktop에서 "표 다음 자리"의 y값이다. (4) 사고 뒤 item/Desktop의 자식 순서가 [표, 이름, 설명]으로 바뀌어 있었다(내가 만든 순서는 [이름, 설명, 표]). 자동 배치 프레임 안에서 레이어를 끌어 옮기면 생기는 꼴이지만, 누가 언제 옮겼는지는 확인하지 못했다.
- 한 일: item/Desktop의 순서를 처음대로 되돌렸다. 스크립트 끝에 자리 검사를 넣었다(flow arrows·flow backdrop이 세트와 같은 자리·크기인지, 안의 것이 세트 범위 안인지, 세트 옆이 아닌 곳에 있는 flow 레이어가 없는지, 흐름도가 섹션 안인지, 섹션끼리 겹치지 않는지. 어긋나면 오류로 멈춤). 섹션 크기와 그 아래 것(돌려 볼 화면)을 옮기는 일도 스크립트가 한다.
- 앞으로: 조립 하나를 고치면 Desktop과 Taskbar 두 섹션을 모두 찍어 직접 본다.

## Taskbar 앱 버튼 우클릭 메뉴

- 문서([[작업 표시줄:우클릭 메뉴]])대로: 앱 이름 · 작업 표시줄에서 제거 · 창 닫기(창 둘 이상이면 모든 창 닫기), 점프 목록이 있으면 그 위에 점프 목록과 구분선. 너비 294, 띠 위 12, 버튼 가운데 위. 메뉴가 열리면 미리보기는 닫힌다. 띠의 빈 곳에는 메뉴가 없다.
- 새 슬롯 `Context menu`를 뒀다. 미리보기와는 함께 열리지 않지만(문서), 패널과의 관계는 문서에 없어 Panel area에 합치지 않았다.
- 견본은 탐색기(창 둘): 고정됨(Project, Blog, About) · 구분선 · 파일 탐색기 · 작업 표시줄에서 제거 · 모든 창 닫기. 항목은 Patterns 견본의 MenuItem과 머리글을 복제하고, 구분선은 MenuSeparator로, 마지막 항목 글자만 '모든 창 닫기'로 바꿨다. 메뉴는 Motion=Enter Up.

## 키보드 흐름도 (사용자 제안·결정)

- 조립마다 흐름도를 둘로 둔다: 원래 흐름도(마우스로 하는 것만)와 키보드 흐름도(키로 하는 것 전부).
- 키로 하는 것은 전부 키보드 흐름도로: Tab·방향키로 포커스 옮기기, Enter·Space·F2·Delete·단축키, Esc로 닫기, 입력 중의 Enter까지. 원래 흐름도에는 키 이름이 하나도 없게. (Esc와 입력 중 Enter를 원래 흐름도에 남기자던 내 안은 버림. 사용자: "섞이기보단 따로")
- 우클릭 같은 마우스 동작의 대체 키도 키보드 흐름도에 나타낸다(사용자). 우클릭 = 포커스한 것에서 Shift+F10·메뉴 키. 코드는 공통(menu-popup)으로 지원하고 문서에는 작업 표시줄 점프 목록 한 곳에만 적혀 있음 → 문서에 공통 규칙으로 적을 것.
- 검사 기준(내가 세움): 원래 흐름도의 화살표마다 키보드로 같은 곳에 닿는 길이 있는지. 문서·코드에 길이 없으면 "키보드로 못 하는 것"으로 보고.
- 조립을 넘나드는 Tab 이동은 Shell의 키보드 흐름도.
- 범주 카드 포커스 선: 타일과 이름을 함께 감싸고 모서리는 각지게(사용자 결정).

## 키 정하기 (사용자와 하나씩, 표는 review/keyboard-map.md)

- 원칙(사용자): 단축키는 내가 혼자 정하지 않는다. 문서에 있는 것은 따르고, 없는 것은 표로 가져가 같이 정한다.
- ㄱ (사용자 결정: "좋아 이렇게 하자") 코드에 이미 있는 키는 그대로 따르고 문서에 적는다: 우클릭 메뉴 = 포커스한 것에서 Shift+F10·메뉴 키(어디서나), 메뉴 안 ↑↓·Enter·→·Esc, 버튼 Enter·Space, 고정 타일 Enter·Space, 이름 바꾸기 Esc 취소·밖 누르기 확정, 미리보기 Esc(포커스는 앱 버튼으로), 범주 폴더 쪽은 포커스를 따라 넘어감.
- ㄴ 남은 것(없음): 빈 곳 메뉴 열기, 선택 지우기, Ctrl+클릭 대체, 끌어서 자리·순서 바꾸기, 창 하나인 앱의 미리보기 열기, 범주 카드 열기·큰 아이콘 포커스, 글자 머리글·격자, Start 여는 단축키.
- ㄷ 남은 것: Tab이 멈추는 차례, 포커스 모습 없는 부품(TaskbarButton, MenuCommandButton, SectionHeader, ProfileButton).
- (사용자 결정) 바탕화면 선택 지우기 = Esc. 열려 있는 것(메뉴, 이름 바꾸기)이 있으면 그것부터 닫고, 아무것도 열려 있지 않을 때 선택을 지운다(순서는 내가 덧붙임).
- (미정) 빈 곳 메뉴 열기: 사용자는 따로 키가 있는 편이 낫다고 보고, "힌트를 어떻게 줄 것인가"를 물음. 키보다 알려 주는 방법이 먼저.

## 키 안내와 논의 방식 (사용자 결정)

- 키 안내는 Windows처럼: 메뉴 항목 옆 단축키 글자, 단추 툴팁(포커스에도), ARIA(낭독기), 그리고 단축키를 모은 글 하나(붙일 데 없는 키까지). Alt 글자 표시는 가져오지 않음. 숨긴 버튼·Tab일 때만 보이는 버튼 안은 버림.
- Windows 조사(Microsoft 문서 원문): 붙일 데 없는 키는 Windows도 화면 안에서 알리지 않고 공식 단축키 목록에만 적음. Ctrl+방향키+Space(떨어진 것 고르기), Alt+Shift+방향키(작업 표시줄 버튼·Start 타일 순서), Ctrl+Shift+N(새 폴더), F5(새로 고침), Win·Ctrl+Esc(Start). 빈 곳 메뉴·선택 지우기·아이콘 칸 옮기기·미리보기 열기·글자 격자·범주 폴더는 목록에 없음. 내 기억 "Ctrl+Space로 선택 해제"는 틀림.
- WCAG 2.5.7: 끌기는 키보드 대체만으로 부족, 누르기만으로 하는 길도 필요. 없는 것: 작업 표시줄 앱 버튼 순서, 바탕화면 아이콘 칸 옮기기.
- 웹에서 못 쓰는 키: Win 조합, Alt, F10 단독, F5, Ctrl+N 등. Alt+Shift+방향키는 시험 필요.
- 논의 방식(사용자): 조립 단위로, 그 조립에서 할 수 있는 기능을 다 나열하고 하나씩 논의한다. Desktop부터.

## Desktop 기능을 하나씩 (정해진 것도 다시 논의, 사용자 요청)

- 1. 아이콘 하나 고르기: 마우스는 누르면 선택(다른 것은 풀림). 키보드는 Tab이 아이콘 묶음에 한 번만 멈추고(고른 것, 없으면 첫 아이콘) 방향키로 선택을 옮김. (사용자 결정) 아무것도 고르지 않은 채 Tab으로 들어오면 첫 아이콘에 포커스만 가고 선택은 안 된다. 문서에 적을 것.
- 2. 이어진 범위 고르기: Shift+누르기는 마지막으로 고른 것부터 누른 것까지 격자 순서(문서대로). Shift+방향키는 처음 고른 것을 기준으로 두고 방향을 바꾸면 줄어든다(사용자 결정). 자동 정렬이 꺼져 흩어져 있어도 격자 순서를 따른다(사용자 결정, 문서대로).
- 2 (미정) Shift+→ 뒤 Shift+↓: 격자 순서로 이어진 범위인가, 네모 범위인가. 사용자가 물음.

## 접근성 원칙과 Desktop 기능 분류 (사용자 결정)

- 원칙: 꼭 있어야 하는 기능은 바탕 키(Tab, 방향키, Enter, Space, Esc)와 눈에 보이는 것만으로 할 수 있어야 한다. 빠른 키는 지름길이라 몰라도 못 하는 일이 없어야 한다. (사용자: "경험으로 아는 것은 경험 없는 사람이 못 쓴다")
- 가르는 기준: 다른 방법으로 같은 결과를 낼 수 없으면 꼭 있어야 하는 것, 되풀이하거나 돌아가면 같은 결과가 나오면 편의.
- Desktop 꼭 있어야 하는 것: 아이콘으로 가서 하나 고르기, 열기, 이름 바꾸기, 삭제, 다른 곳으로 옮기기(잘라내기→붙여넣기), 휴지통 비우기, 새 폴더, 정렬 기준, 자동 정렬, 아이콘 크기, 다른 칸으로 옮기기, 메뉴 안에서 움직이기.
- Desktop 편의: 여러 개 고르기(범위·끌기·떨어진 것·모두), 끌어 놓기, 빠른 키(F2, Delete, Ctrl+X/V, Ctrl+Shift+2·3·4, Shift+F10), 선택 지우기(Esc), 새로 고침.
- 막힌 곳 셋: 아이콘 메뉴를 여는 눈에 보이는 길, 빈 곳 메뉴를 여는 눈에 보이는 길, 칸 옮기기.
- 미정(편의 쪽, 나중에): Shift+방향키가 고르는 방식(내 의견: 지나간 것만), 떨어진 것 더 고르기(Windows: Ctrl+방향키+Space).

## 접근성 모드와 접근성 패널 (사용자 제안)

- 막힌 곳(아이콘 메뉴·빈 곳 메뉴를 여는 눈에 보이는 길)을 "더 보기(⋯)" 단추가 아니라 접근성 패널로 푼다. 화상 키보드·AssistiveTouch 같은 종류.
- 접근성 모드를 켜면 패널이 뜬다. 패널은 가로로 긴 띠이고 글자 없이 아이콘 단추만 있다. 네 구석(우상·우하·좌상·좌하) 가운데 고른 곳에 둔다.
- 패널의 차례: 먼저 지금 고른 것에 할 수 있는 일(아이콘이면 열기, 이름 바꾸기, 잘라내기, 삭제), 그다음 그 조립(Desktop)에서 할 수 있는 일(새로 만들기 등).
- Tab이나 단축키로 패널의 단추를 바로 고를 수 있다.
- 켜는 길: 바탕화면에 "접근성 모드"라는 이름의 아이콘을 둔다. 누르면 켜지고 다시 누르면 꺼진다. (작업 표시줄 시계 옆 단추로 두자던 내 안 대신)
- 모든 조립에 통하는 것이라 Shell의 것. 조립은 "지금 고른 것에 할 수 있는 일"을 손잡이로 연다.
- (사용자 결정) 창이 바탕화면을 덮을 때를 위한 켜는 길은 Start가 아니라 작업 표시줄에 둔다.
- (사용자 결정) 켜짐·꺼짐은 아이콘으로 표시한다.
- (사용자 결정) 고른 것이 없어도 포커스는 있다. 패널은 "지금 포커스가 있는 곳에 우클릭한 것"과 같다. 바탕화면에 아무것도 고르지 않았으면 빈 곳 우클릭 메뉴의 내용이 나온다.
- (사용자 결정) 패널은 아이콘 단추만. 무엇인지는 올렸을 때의 툴팁으로 알린다(공간을 줄이고 접근성도 지킴). 툴팁은 문서대로 포커스가 가도 뜬다(이름 (단축키)).
- 미정: 작업 표시줄의 어느 자리인지, 바탕화면 아이콘도 같이 두는지, 하위 메뉴가 있는 항목(보기·정렬 기준·새로 만들기)을 패널에서 어떻게 여는지, 터치에서 툴팁, 켜짐·꺼짐 아이콘 자산.
- (사용자 결정) 접근성 모드는 바탕화면 아이콘과 작업 표시줄(가운데 영역의 고정 앱 버튼) 둘 다에 둔다.
- (사용자 결정) 접근성 모드는 앱이다. Start의 모두 목록·범주 보기(앱)·검색에도 나온다. 접근성 패널이 그 앱의 창이고, 켜고 끄는 것은 앱을 열고 닫는 것. 켜짐은 작업 표시줄 버튼의 밑줄(실행 중 표시)로도 드러난다.
- (사용자 결정) 바탕화면의 접근성 모드 아이콘은 휴지통처럼 다룬다: 지울 수 없고, 옮길 수 없고, 이름을 바꿀 수 없다. 메뉴는 열기(켜져 있으면 닫기)만. 자리는 휴지통 바로 다음.
- 미정: 작업 표시줄의 접근성 모드 버튼도 고정을 풀 수 없게 할지.
- (사용자 결정) 작업 표시줄의 접근성 모드 버튼은 다른 앱 버튼처럼 지울 수 있다(고정 해제 가능). 고정을 풀 수 없게 하자던 내 안은 버림. 풀어도 바탕화면 아이콘(지울 수 없음)과 Start·검색으로 닿는다.
- (사용자 결정) 패널의 포커스: 지금 있는 곳에서 Tab → 패널(한 번만 멈춤) → 다시 Tab → 패널이 없었을 때 갔을 다음 자리. 패널 안은 ←→, 누르기는 Enter·Space, 돌아가기는 Esc·Shift+Tab. 일이 끝나면 포커스는 원래 있던 곳으로.
- (내 판단) 패널은 "지금 있는 곳 바로 다음"에만 끼어든다. 다음 자리에서 Shift+Tab으로 되돌아올 때는 패널을 거치지 않고 원래 자리로 간다.
- (고침, 사용자 결정) 패널의 포커스: Tab은 평소대로 움직인다. 패널은 Tab의 흐름에 끼어들지 않고 차례의 한 자리(그 조립의 맨 끝)로만 있다. "지금 있는 곳 바로 다음에 끼어든다"는 버림(사용자: 사용성에 불편). Shift+Tab·Ctrl+Tab은 쓰지 않는다(뒤로 가기, 브라우저 탭 넘기기).
- (사용자 결정) 패널로 바로 가는 키를 따로 둔다. 어떤 키인지는 마지막에 정한다(브라우저에서 실제로 되는지 시험한 뒤).
- (사용자 결정) 그 키는 패널이 열릴 때 안내한다(낭독기가 읽게). 눈으로 보는 사람은 패널을 바로 고르면 되니 따로 안내하지 않아도 된다.
- 패널 안: ←→로 옮기고 Enter·Space로 누르고 Esc로 원래 자리로.
- (사용자 결정) 하위 메뉴가 있는 항목(보기·정렬 기준·새로 만들기)은 패널에서 아이콘 단추 하나이고, 누르면 단추 옆에 우클릭 메뉴의 하위 메뉴와 같은 메뉴가 그대로 뜬다(글자 있는 보통 메뉴, 방향키·Enter). 패널이 아래 구석이면 위로, 위 구석이면 아래로.
- (사용자 결정) 패널의 자리: 패널 맨 끝에 "자리 옮기기" 단추(누르면 네 구석 메뉴, 지금 자리에 표시)와 "닫기" 단추(접근성 모드 끔). 패널의 단추는 세 묶음: 고른 것에 할 일 / 지금 있는 곳에 할 일 / 패널 자체. 처음 자리는 오른쪽 아래(작업 표시줄 바로 위). 고른 자리는 기억한다(방문자 저장).
- (사용자 결정) 접근성 모드 앱 아이콘은 새로 그린다(Windows의 접근성 그림처럼 사람 모양, 다른 앱 아이콘과 같은 급). 켜짐·꺼짐은 색이나 작은 표시로 구별. 패널의 "자리 옮기기" 아이콘도 새로 필요. 피그마 Foundations에는 접근성·자리 옮기기 아이콘이 없고 닫기는 있음.
- (논의 중) 터치에는 올리기가 없어 툴팁이 안 뜬다. 사용자: "그냥 텍스트로 나타내게 할까? 어차피 나올 게 많진 않다". 실제 수: 폴더 아이콘 7 + 바탕화면 4~5 + 패널 자체 2 = 13~14.
- (사용자 결정) 패널의 모습: PC·노트북은 가로로 긴 띠에 아이콘만(올리면 툴팁). 모바일은 글자를 붙여 세로로 쌓은 목록. 모바일의 세부(접혀 있다 펼치기 등)는 모바일을 그릴 때.
- (사용자 제안) 모바일의 패널: 평소에는 아이콘만 있고, "확장" 단추를 누르면 오른쪽이나 왼쪽으로 넓어지면서 글자(어떤 단추인지)가 나온다. 접으면 다시 아이콘만. 세부는 모바일을 그릴 때.
- (논의 중) 아이콘을 다른 칸으로 옮기는 길: 내 의견은 아이콘 메뉴에 "이동"(위·아래·왼쪽·오른쪽) 항목. 자동 정렬이 꺼졌을 때만, 갈 수 없는 방향은 빼고, 찬 칸이면 맞바꾸기.
- (사용자 결정) 패널의 기본 모습(PC·모바일 공통): 기본은 아이콘만. `<` 단추를 누르면 패널이 늘어나면서 각 아이콘 옆에 이름이 나온다. 다시 누르면 줄어든다. PC는 가로 띠, 모바일은 세로 띠로 방향만 다르다.
- (사용자 결정) PC에서는 툴팁도 그대로 나온다(올리거나 포커스가 가면 `이름 (단축키)`).
- 패널의 단추 차례: [펼치기·접기] / 고른 것에 할 일 / 지금 있는 곳에 할 일 / [자리 옮기기] [닫기].
- (사용자 결정) 아이콘을 다른 칸으로 옮기는 길: 아이콘 메뉴에 "위로·아래로·왼쪽으로·오른쪽으로 이동" 항목. 자동 정렬이 꺼졌을 때만 나오고, 갈 수 없는 방향은 빼고, 메뉴에 있으니 접근성 패널에도 나온다. 찬 칸으로 가면 두 아이콘의 자리를 맞바꾼다(내 제안, 반대 없음). 잘라내기→붙여넣기로 옮기자는 안은 빈 칸에 못 두는 한계 때문에 사용자가 거둠.
- Desktop의 꼭 있어야 하는 것은 모두 길이 생김. 남은 것은 편의 쪽 키.
- (사용자 결정, 편의) Shift+방향키는 "지나간 것만" 고른다(ㄷ). 왔던 길을 되돌아가면 방금 고른 것이 풀린다. 마우스의 Shift+누르기는 문서대로 격자 순서 범위(달라도 됨).
- (사용자 결정, 편의 쪽 정리) 접근성 패널이 있으니 키보드의 편의 키를 새로 늘리지 않는다. Shift+방향키는 둔다("지나간 것만" 방식 그대로). Ctrl+방향키+Space(떨어진 것 더 고르기)는 넣지 않는다. 새 기능의 빠른 키(새 폴더, 칸 옮기기 등)도 만들지 않는다. 이미 문서에 있는 빠른 키(F2, Delete, Ctrl+X/V, Ctrl+A, Ctrl+Shift+2·3·4, Shift+F10)는 그대로 둔다. 선택 지우기는 Esc.
- 새로 정해야 하는 키는 접근성 패널로 바로 가는 키 하나(맨 마지막에).
- (사용자 결정, 키의 기준) 둘 수 있는 키는 세 가지: 바탕 키(Tab, 방향키, Enter, Space, Esc), 알려 줄 자리가 있는 키(툴팁·메뉴에 적히는 F2, Delete, Ctrl+X/V, Ctrl+Shift+2·3·4), 어디서나 똑같이 쓰는 키(Ctrl+A, Shift+방향키). 이 블로그에서만 통하는 숨은 키는 만들지 않는다(Ctrl+방향키+Space, 새 기능의 빠른 키).
- Desktop 키 정리 끝. Shift+방향키는 지나간 것만, 되돌아가면 풀림.
- 다음: Taskbar를 같은 방식으로(기능 다 나열 → 꼭 있어야 하는 것/편의 → 패널로도 안 풀리는 것만 논의).

## Taskbar 기능 (조립 단위 논의)

- 꼭 있어야 하는 것 가운데 바탕 키로 되는 것: Start 열고 닫기, 검색, 앱 열기·창 전환, 창 여럿일 때 창 고르기(Enter→방향키→Enter), 고정·빼기와 창 닫기(접근성 패널).
- (사용자 결정) 앱 버튼 순서 바꾸기: 앱 버튼 메뉴에 "왼쪽으로 이동 · 오른쪽으로 이동" 항목. 갈 수 없는 방향은 빼고, 같은 무리(고정/실행 중) 안에서만. 패널에도 나온다.
- 정할 것: 여러 창 가운데 하나만 닫기(지금 카드에서 Delete뿐), 점프 목록의 항목 열기·빼기를 패널에서 어떻게.

## 접근성 패널을 단순하게 (사용자 결정: "굳이 복사 같은 걸 넣기보단")

- 패널은 우클릭 메뉴의 항목을 늘어놓지 않는다. "우클릭을 대신 눌러 주는 단추"만 갖는다: [고른 것의 메뉴 열기] [지금 있는 곳의 메뉴 열기] + 패널 자체의 [자리 옮기기] [닫기]. 누르면 우클릭했을 때의 메뉴가 그 자리에 뜨고 포커스가 메뉴 안으로 간다. 그 뒤는 메뉴 그대로(방향키, Enter).
- 버려진 것: 항목 전부를 아이콘 단추로, `<` 로 펼치기, 하위 메뉴가 있는 단추 옆에 메뉴 띄우기, 모바일 세로 목록, 툴팁에 기대기. 단추가 몇 개 안 되니 글자로 적는다.
- 그대로인 것: 접근성 모드는 앱(패널이 그 창), 켜는 길(바탕화면 아이콘·작업 표시줄 버튼·Start·검색), 켜짐 표시, 네 구석 자리, Tab은 평소대로 + 패널로 가는 키는 맨 마지막에.
- Taskbar: (사용자 결정) 미리보기 안에서 Tab이 카드마다 [열기][닫기] 두 자리를 돌고(무한 루프) Esc로 나온다. 닫기 버튼은 키보드로 닿는다(문서 "접근성: 역할"의 창 미리보기 카드 부분을 고침. 탭·Snap Assist 카드는 창을 볼 때). Delete는 빠른 키로 남김(닫기 버튼 툴팁에 적힘). 카드는 여는 버튼과 닫는 버튼이 나란한 둘.
- Taskbar: (사용자 결정) 점프 목록은 패널의 단추로 열면 앱 버튼 위(우클릭했을 때의 자리)에 메뉴가 뜨고 포커스가 그리로 간다.
- 미정: 점프 목록에서 항목 빼기(내 의견: 그 줄에서 →로 압정 버튼, Enter).
- (사용자 결정) 점프 목록에서 항목 빼기도 패널로: 그 줄에 포커스 → 패널의 [그 항목 메뉴] → 문서에 이미 있는 항목 메뉴(열기 / 이 목록에서 고정 해제). →로 압정 버튼에 가자는 내 안은 버림.
- (사용자 결정, 패널의 규칙) 포커스가 접근성 패널로 옮겨 가도 열려 있던 것(메뉴, Start, 검색, 미리보기)은 닫히지 않는다. 패널은 "밖"이 아니다. 패널은 패널로 오기 직전에 포커스가 있던 것에 대해 일한다. 패널에서 Esc는 원래 자리로(열려 있던 것은 그대로). 문서의 "포커스가 밖으로 나가면 닫힌다"에 예외로 적을 것.
- Taskbar 정리 끝. 다음: Start.

## Start 기능 (조립 단위 논의)

- 바탕 키로 되는 것: 타일·항목 열기, 보기 바꾸기, 다시 시작, 검색, 범주 폴더 안. 접근성 패널로 풀리는 것: 타일·항목의 메뉴(고정·빼기·이동·링크 복사).
- (사용자 결정) 범주 카드: 방향키로 카드에서 카드로, Enter는 범주 폴더 펼치기 하나. 카드 안 큰 아이콘으로 바로 여는 것은 키보드에 두지 않는다(펼친 뒤 여는 것과 같은 결과라 편의). 카드 전체가 하나의 누를 것.
- (사용자 결정) 글자로 건너뛰기(편의): 글자 머리글도 목록의 한 줄처럼 방향키로 멈춘다. 머리글에서 Enter → 글자 격자. 격자에서 방향키로 글자 사이, Enter → 그 글자 자리로, Esc → 그냥 돌아감. SectionHeader에 포커스 모습을 더해야 함.
- Start 정리 끝. 다음: Search.
- Search: 정할 것 없음(결과 ↑↓·Enter, 카드의 단추는 Tab·Enter, 입력 전 항목은 Tab·Enter. 우클릭 메뉴 없음).
- 포커스 모습을 더할 부품(같은 방식): TaskbarButton, MenuCommandButton, SectionHeader. 미리보기 카드의 닫기 버튼에 포커스가 간 모습도 확인해 없으면 더함.
- (사용자 결정) ProfileButton은 시계처럼 다룬다: 눌러도 아무 일이 없으니 Hover를 빼고 포커스도 받지 않는다("일단 빼자").
- (사용자 결정) Tab이 멈추는 차례: 화면에 보이는 차례대로(위→아래, 같은 높이면 왼→오). Desktop: 아이콘 묶음. Taskbar: 시작 버튼 → 검색 상자 → 앱 버튼 묶음. Start: 검색칸 → 고정됨 → 보기 버튼 → 모두 목록 → 전원 버튼. Search: 결과 항목마다 → 카드의 열기·링크 복사. 미리보기: 카드마다 열기 → 닫기(루프). 메뉴: 방향키. 시계·프로필은 멈추지 않음. 화면 전체: 바탕화면 → (창) → 작업 표시줄 → 접근성 패널(자리와 상관없이 늘 맨 끝) → 처음. 조립을 넘나드는 세부는 Shell을 만들 때.
- 남은 결정: 접근성 패널로 바로 가는 키(브라우저 시험 뒤).

## 패널로 가는 길 (다시 논의해 고침, 사용자 결정)

- 패널을 고정된 자리(맨 끝, 작업 표시줄 앞)에 두는 안은 성립하지 않음: Tab으로 거쳐 가는 동안 포커스가 바뀌어 패널의 대상이 바뀐다(사용자 지적). 패널 바로 앞의 것만 대상이 될 수 있다.
- Tab: 지금 있는 것에서 Tab을 누르면 패널로, 한 번 더 누르면 패널이 없었을 때 갔을 곳으로(사용자의 처음 제안). 단, 패널에 나올 것(우클릭 메뉴)이 있는 것에서만 끼어든다. 예: 아이콘 → [패널] → 시작 버튼 → 검색 상자 → 앱 버튼 → [패널] → 처음.
- 그 자리에서 우클릭 메뉴를 여는 키는 Shift+F10(메뉴 키도). 원래 Windows와 브라우저가 우클릭을 키보드로 하는 키. 패널의 단추에 이 키를 적어 알린다. "패널로 바로 가는 키"는 따로 만들지 않는다.
- Ctrl+Space는 후보였으나 macOS의 입력 소스 전환과 겹칠 수 있어 접음. Shift+F10이 Mac에서 듣는지는 코드로 만들 때 시험(F10이 소리 끄기).
- 앞의 "Tab 차례" 결정에서 "패널은 늘 맨 끝"은 이 결정으로 대체.

## 패널과 키 (최종, 사용자 확인: "맞아")

- Tab은 원래대로. 패널 때문에 달라지지 않는다. 패널이 끼어들지 않는다(앞의 "메뉴가 있는 것에서만 끼어든다"는 버림).
- Shift+F10(메뉴 키)은 패널의 메뉴 단추의 단축키다: 지금 포커스가 있는 것의 우클릭 메뉴를 그 자리에서 연다. 패널까지 가지 않는다. 패널의 단추에 이 키가 적혀 있다(F2가 이름 바꾸기 단추의 단축키인 것과 같은 관계).
- 패널은 그 단추와 키를 눈에 보이게 해 주는 것. 마우스로는 눌러 쓰고 키보드로는 적힌 키를 보고 누른다.
- 패널 자체의 단추(자리 옮기기, 닫기)는 Tab 차례의 맨 끝.
- 원칙을 고침: 꼭 있어야 하는 기능은 바탕 키, 또는 화면에 적혀 있는 키만으로 할 수 있어야 한다.
- Mac에서 Shift+F10이 듣는지는 코드로 만들 때 시험. 안 되면 Mac용 키를 정하고 패널에 적히는 글자만 바꿈.
- "패널로 포커스가 가도 열려 있던 것은 닫히지 않는다"는 마우스로 패널을 누를 때에도 필요하므로 그대로 둔다.

### 내가 정한 세부 (사람이 확인할 것)

- 패널의 Shift+F10 글자: 고른 것이 있으면 '고른 것의 메뉴' 옆, 없으면 '지금 있는 곳의 메뉴' 옆에 적음.
- 패널이 가리키는 곳에 메뉴가 없으면 그 단추는 Button의 Disabled 모습(작업 표시줄 · Start에는 빈 곳 메뉴가 없다). 빼는 편이 나은지는 미정.
- 패널의 포커스가 있는 곳 변형은 셋으로 묶음: 고른 것 + 빈 곳(바탕화면 아이콘) / 빈 곳만(아무것도 안 고름) / 고른 것만(앱 버튼, Start 타일은 모습이 같아 하나).
- 자리 메뉴는 아래 구석에서는 패널 위로, 위 구석에서는 패널 아래로 연다. 패널 자체는 구석에 놓지 않고(조립은 패널만) 자리는 설명과 Shell의 흐름 줄에 적음.
- 이동 항목의 자리: Desktop은 목록 맨 아래 구분선 뒤, Taskbar는 고정 항목 다음 줄.
- Desktop 이동 항목은 아이콘 없이 글자만(아래 화살표 자산이 없다). Taskbar는 왼쪽 · 오른쪽 화살표 아이콘을 씀.
- 접근성 모드를 여는 마우스 동작은 다른 아이콘처럼 더블클릭으로 적음.
- 아무것도 고르지 않고 첫 아이콘에 포커스만 있을 때 Shift+F10은 빈 곳 메뉴를 연다("고른 것이 없으면 빈 곳 메뉴" 결정대로).
- Ctrl · Shift를 누른 채 마우스로 누르는 것은 마우스 흐름에 둠(검사에서 키로 치지 않음).
- 키로만 닿는 모습(모두 선택됨, 포커스 모습들)은 키보드 흐름 그림에 놓이고, 거기서 나가는 마우스 흐름도 그 그림에 같이 그려진다.

## 남은 조립 논의 (창, 탐색기, Chrome, Windows)

- 1. (사용자 제안, 내가 확인 후 동의) 창은 조립이 아니라 부품 `WindowFrame`이다. 조립은 `Chrome`, `Explorer`로 나누고 각자 창 틀을 안에서 쓴다. 창 하나 안에서 끝나는 기능(옮기기, 크기 바꾸기, 최대화·복원)은 부품의 "동작"(동작의 종류, behaviors/)으로 둔다. 코드에서 한 번 만들어 같이 쓰므로 Chrome·Explorer에 반복되지 않는다. 내 "Windows가 가져야 반복이 없다"는 피그마 흐름도 관점을 코드에 그대로 옮긴 잘못이었음. 가르는 기준: 부품 혼자 끝나는 것은 동작, 부품 여럿·주변을 알아야 하는 것은 조립의 흐름.
- 진행 순서(사용자 알림): 조립을 먼저 다 정하고(Chrome → Explorer → 다시 시작 → Windows) 그다음 조립을 보고 부품을 재정비한다.
- Chrome 1. (사용자 동의) `<Chrome>` 조립은 브라우저 겹(탭 줄, 도구 모음, 찾기 막대, 확대/축소, ⋮ 메뉴)까지만 갖고 페이지는 슬롯이다. 조립이 페이지에 넘기는 것은 페이지 자리의 너비(넓은·좁은)와 배율뿐. Notion 글뿐 아니라 어떤 내용도 넣을 수 있다.
- Chrome 1-2. (사용자 동의) 새 탭 페이지는 `<Chrome>`의 기본 제공 내용(바로가기에 넣을 것만 앱이 넘김). 글 화면은 따로 조립 `<Article>`(틀: 목차 자리·본문 폭·넓은/좁은, 기능: 읽는 위치 표시·이미지 크게 보기. Chrome을 모름). 검색 결과·찾을 수 없음은 앱이 부품으로 엮음.
- Chrome 2. (사용자 동의) 영역은 `ChromeTabs`, `ChromeToolbar`, `ChromeFindBar`, `ChromePage`(슬롯). 탭 줄·도구 모음은 슬롯이 아니고 ⋮ 메뉴의 항목만 슬롯. 찾을 수 없음 화면은 앱이 아니라 Chrome이 주는 블록 `<ChromeNotFound>`(없는 주소인지 판단은 앱, 놓는 곳은 페이지 자리)로 고침. Chrome이 주는 페이지는 새 탭·찾을 수 없음, 앱이 만드는 것은 검색 결과. 찾기와 확대/축소는 페이지 내용을 모른 채 Chrome이 다 함.
- Chrome 3. (사용자 동의) 기능을 셋으로 가름: 조립의 흐름(탭 전환·닫기·새 탭·순서·넘침·탭 검색, 뒤로·앞으로, ⋮ 메뉴, 찾기 막대, 확대/축소, 넓은·좁은), 부품의 동작(창 틀, 주소창, 버튼·탭·메뉴), 앱의 일(주소 해석, 추천 내용, 새로고침, 마지막 탭 닫힘·휴지통 글은 Windows). 뒤로·앞으로 기록은 Chrome이 탭마다 갖고 앱이 값으로 대신 가질 수 있음.
- 부품의 동작도 흐름으로 나타낸다(사용자 지적 후 합의). 자리는 그 부품 옆의 작은 흐름도, 한 번만. 눌림·올림·포커스처럼 모든 부품에 같은 것은 그리지 않음(State 축). 조립의 기능이 부품의 동작 뒤에 이어지면 조립 흐름도에 그 상태의 모습을 놓고 거기서부터 화살표, 앞길은 "○○의 동작"이라고만 적음. 부품에 흐름도를 붙이는 일은 부품 재정비 때 함. 재정비 목록: WindowFrame(옮기기·크기·최대화), AddressBar(전체 선택·추천 펼침·줄 고르기·Esc).
- Chrome 4-1. (사용자 결정) 탭 닫기는 메뉴가 아니라 닫기 버튼(×)으로: 고른 탭에서 Tab을 누르면 그 탭의 × 버튼, Enter·Space로 닫음(미리보기 카드의 [열기][닫기]와 같은 방식). Delete는 그대로 두고 × 버튼 툴팁에 `닫기 (Delete)`. 닫은 뒤 포커스는 새로 골라진 탭. 탭 우클릭 메뉴에는 `왼쪽으로 이동`·`오른쪽으로 이동`만(끝이면 숨김). 탐색기 탭도 같음.
- Chrome 4-2. (사용자 동의) ⋮ 메뉴의 확대/축소 줄: ↓로 줄에 오면 − 에 포커스, ← →로 − 와 + 사이, Enter·Space로 누름(메뉴 안 닫힘), 비활성 쪽은 건너뜀, ↑ ↓로 다른 줄. Ctrl + `+`·`-`·`0`은 그대로(− + 단추 툴팁에 적음, Ctrl+0은 어디서나 쓰는 키로 봄). 100% 글자를 단추로 만들지 않음.
- Chrome의 Tab 차례(화면 차례 규칙 그대로, 내가 정함): 탭 검색 버튼 → 고른 탭 → 그 탭의 × → 새 탭 버튼 → 창 버튼(최소화·최대화·닫기) → 뒤로 → 앞으로 → 새로고침 → 주소창 → ⋮ → 찾기 막대(입력칸 → 이전 → 다음 → 닫기, 열렸을 때) → 페이지 안.
- Chrome 모바일: 다른 조립과 같이 뒤로 미룸(모바일·노트북 변형은 조립을 다 정한 뒤 한꺼번에).
- Article 1. (사용자 제안, 동의) 영역: 커버, 머리, 목차, 본문, 꼬리. 기본은 `<Article>`에 값(커버, 제목, 작성일, 폴더, 이전·다음 글)을 넘기면 정해진 모습으로 바로 그려지고, `<ArticleCover>…</ArticleCover>`처럼 영역 블록을 직접 넣으면 그 영역만 커스텀으로 바뀐다(기본 제공 = 슬롯의 기본 내용). 본문은 늘 앱이 채움. 목차는 Article이 본문의 제목을 읽어 스스로 그리고 읽는 위치를 따라감. 넓은·좁은 모양은 Article이 자기 자리의 너비로 가름(Chrome이 너비를 넘기지 않음, Chrome이 넘기는 것은 배율뿐).
- Article 2. (사용자 동의) Article의 흐름: 읽는 위치를 목차에 표시, 목차 항목 누르기 → 그 제목으로, 이미지 누르기 → 크게 보기(글 영역을 덮음, Esc·닫기·바탕 누르기로 닫힘, 포커스는 안에 머묾). 이미지 부품은 눌림만 알림. 앱의 일: 글 속 링크, 이전·다음 글. 키보드는 바탕 키뿐.

## Windows 논의 → 조립으로 두지 않음 (사용자 지적: 맨 위 그릇은 디자이너가 아니라 개발자의 관점)

- `Windows`는 피그마 조립으로 만들지 않고 디자인 시스템의 조립 목록에서 뺀다. 코드에서 맨 위에 무엇을 두고 상태를 어디 둘지("조립이 알리고 맨 위가 띄운다" 포함)는 개발 쪽이 정한다. 앞서 정한 `<Windows>` 이름과 `assemblies/windows`는 "디자인 시스템이 주는 조립"이 아니라 개발 쪽에서 엮는 것으로 자리를 옮겨 적는다.
- Windows에 넣으려던 기능은 그것이 시작되는 조립에 넣고 흐름도에 끝까지 그린다: 아이콘을 열면 창이 뜸(Desktop), 앱 버튼으로 최소화·복원·맨 앞(Taskbar), 다시 시작(Start), 알림 상자(뜨는 조립: Explorer·Chrome·Desktop), 탐색기에서 글을 열면 Chrome 창(Explorer), 마지막 탭 닫으면 창 닫힘(Chrome·Explorer). "Windows의 일"·`Windows의 흐름:` 글줄로 끊어 둔 곳을 모습과 화살표로 채운다(테스트 케이스로 읽히게).
- 접근성 패널은 조립이 아니라 부품(`AccessibilityPanel`, Shell 페이지). 패널 혼자의 일(자리 옮기기, 네 구석, 닫기)은 부품의 동작이고 `Patterns / AccessibilityPanel`의 흐름도는 부품 재정비 때 부품 옆으로 옮긴다. 각 조립의 키보드 흐름도에 패널을 거쳐 가는 길을 더한다(패널이 그 조립 화면 구석에 보이는 모습 → 메뉴 단추 → 그 자리에 메뉴). 켜는 길은 켜는 곳마다(Desktop 아이콘, Taskbar 앱 버튼, Start, Search). 흐린 단추도 그 조립에. 모든 메뉴 모습에 패널을 그리지는 않고 조립마다 한 번.
- 조립은 일곱: Desktop, Taskbar, Start, Search, Chrome, Article, Explorer.
- 남은 셋(어느 조립에도 넣기 어려움): 뒤 창을 누르면 맨 앞, 스냅과 Snap Assist, 조립 사이 Tab 차례 → 어디에 그릴지 논의 중.
- (사용자 결정) 스냅과 맨 앞은 Chrome과 Explorer 흐름도에 둘 다 그린다(뒤에 다른 창이 깔린 모습으로). Tab 차례만을 위해 조립 `Windows`를 따로 하나 만든다("이때 windows가 필요하지"). 즉 `Windows` 조립은 남되 화면 전체의 Tab 차례를 그리는 자리다. Screens에 화면의 흐름을 그리자던 내 안은 버림. 조립은 여덟: Desktop, Taskbar, Start, Search, Chrome, Article, Explorer, Windows.
- (사용자 결정, 바로 앞 줄을 고침) 스냅, 맨 앞, Tab 차례를 모두 조립 `Windows`에 그린다. Chrome·Explorer 흐름도에 스냅·맨 앞을 넣지 않는다. `Windows` 조립 = 화면 전체(바탕화면 + 작업 표시줄 + 창 둘 이상 + 접근성 패널)에서, 창이 둘 이상이거나 화면 전체여야 성립하는 일을 그리는 자리. 조립 하나에서 끝나는 일은 그 조립에(아이콘을 열면 창이 뜸, 최소화·복원, 다시 시작, 알림 상자 등은 앞 결정 그대로).
- (사용자 동의) 화면 전체의 Tab 차례: 바탕화면 아이콘 → 맨 앞 창 → 작업 표시줄 → 처음으로. 창은 맨 앞 창 하나만 차례에 들어가고, 다른 창으로는 작업 표시줄 앱 버튼에서 Enter(맨 앞으로 오고 포커스가 그 창 안으로). 최소화된 창은 차례에 없음.
- (사용자 지적, 동의) 접근성 패널은 Tab 차례에 넣지 않는다(앞의 "패널 자체의 단추는 Tab 차례의 맨 끝"과 "패널에서 Esc로 돌아감"을 버림). 자리 옮기기는 접근성 모드 앱의 메뉴(바탕화면 아이콘·작업 표시줄 앱 버튼의 우클릭 메뉴, 켜져 있을 때)에 `패널 자리` 하위 메뉴(오른쪽 아래·왼쪽 아래·오른쪽 위·왼쪽 위, 지금 자리 표시)로 둔다. 닫기는 그 메뉴의 `닫기`나 앱을 다시 누르기. 마우스·터치는 패널의 자리 옮기기·닫기 단추를 그대로 씀.
- (사용자 동의) 창을 다루는 키보드: 최대화 버튼에 포커스가 가면 마우스를 올렸을 때처럼 스냅 레이아웃 메뉴가 뜬다. ↓로 메뉴 안, 방향키로 칸 사이, Enter로 그 칸에 스냅(남은 칸이 있으면 Snap Assist), 최대화 버튼에서 Enter는 최대화, Esc로 메뉴 닫음. 창 옮기기·크기 바꾸기는 키보드에 두지 않는다(스냅 칸과 최대화로 같은 결과, 자유롭게 옮기는 것은 마우스의 편의). 창 틀 부품의 모습은 부품 재정비 때 맞춤.
- 조립 논의 끝. 조립 여덟: Desktop, Taskbar, Start, Search, Chrome, Article, Explorer, Windows. 다음은 부품 재정비.
