2026-11-26에 사용자와 Screens를 하나씩 검토하며 정한 방향이다. 2026-11-28에 `.codocs`에 모두 반영하고 커밋했다(아래 "문서 반영 전"이라는 표시는 옛 것이다). 지금 상태와 이어 할 일은 [[figma-review-handoff]].

- 디자인 시스템의 한 문장 정의(사용자와 합의): "한 번 내린 디자인 결정을, 디자인과 코드가 같은 이름으로 다시 쓰게 하는 약속."
- 이 피그마 파일은 Windows 스타일 디자인 시스템이고 블로그는 채워 넣는 내용이다. 조립과 화면의 틀도 디자인 시스템에 속한다.
- "조립"의 뜻을 바꿨다: 앱이 부품을 엮는 일이 아니라, `<Desktop>`·`<Taskbar>` 같은 디자인 시스템이 주는 이름 있는 그릇이다. 틀·부품 사이 규칙·상태를 갖고 자식으로 부품을 받는다. 앱은 안을 채우고 이벤트에 답한다.
- 조립은 자기 상태를 스스로 갖고 손잡이(예: `useDesktop()`)를 연다. 앱은 손잡이를 꽂거나 값을 넘겨 대신 갖는다.
- 부품은 독립이다(어디에 놓이는지 모름). 메뉴 같은 것은 통으로 주지 않고 블록(Menu, MenuItem, MenuSeparator)으로 엮는다.
- 조립의 기능은 피그마의 흐름(프로토타입 reactions)으로 나타낸다. 기능마다 화살표를 적어도 하나, 대표 길 하나만. 필요한 모습(변형)은 더 만든다. 정확하지 않은 화살표는 걸지 않고, 모르는 것은 지어내지 않는다.
- 흐름도 꼴(사용자가 "이거야, UI 맘에 든다"고 승인): 가로 방향, 기본 모습이 맨 왼쪽, 갈라지는 것은 같은 열에 위아래로, 화살표와 글자는 걸린 reactions를 읽어 스크립트로 그린다, 돌아가는 흐름은 모습 아래 글줄, 모습마다 이름표. 격자 나열은 구분이 안 된다고 거절했다.
- 시험 제작: Patterns의 섹션 `Desktop (조립)`(`6016:8851`), 세트 `6016:8883`. 스크립트는 세션 scratchpad의 `review/draw-flow-arrows.js`(지워질 수 있음).

**Why:** 조립을 앱에 두니 입력이 불어나고 움직임·기능의 자리가 흐렸다. 사용자가 직접 이 구조를 제안했다.

**How to apply:** 다른 조립(Taskbar, Start, 검색, 탐색기, Chrome, 창)도 같은 꼴로 검토·제작한다. 논의는 하나씩 하고([[decide-and-run-delegated-work]]), 사용자와 브라우저 창의 피그마를 같이 보며 진행한다. 내 안이 "통으로 굳히기"나 "앱에 맡기기"로 기울면 이 방향과 어긋나는지 먼저 확인한다.

## 진행 순서 (2026-11-27 사용자가 알림)

- 조립을 먼저 다 정한다(Chrome, Explorer, 다시 시작, Windows 순). 그다음에 조립들을 보고 컴포넌트(부품)를 다시 정비한다. 조립을 논의하는 동안 부품을 고치자는 안을 앞세우지 않고, 부품에서 걸리는 것은 적어 두었다가 재정비 때 꺼낸다.
- 창은 조립이 아니라 부품 `WindowFrame`이고 옮기기·크기 바꾸기·최대화는 부품의 "동작"이다. 조립은 `Chrome`, `Explorer`. 가르는 기준: 부품 혼자 끝나는 기능은 동작(`behaviors/`), 부품 여럿이나 주변을 알아야 하는 기능은 조립의 흐름. 맨 위 조립 이름은 `Windows`, 조립은 `src/assemblies/`, 피그마는 조립마다 `Patterns / <이름>` 페이지.

- 사용자는 조립의 흐름도를 e2e 테스트 케이스로 쓸 생각이다(2026-11-27, "이 흐름도가 결국 테스트 케이스"). 그래서 조립의 흐름도는 그 조립만 보고도 빠짐없이 읽혀야 한다. 다른 조립과 겹치는 기능(예: 탐색기 본문의 선택·이름 바꾸기)도 "○○과 같다"로 줄이거나 따로 떼지 않고 그 조립에 다시 그린다. 화살표 하나가 "어느 모습에서 무엇을 하면 어느 모습" 한 걸음으로 읽히게 한다.

## 키보드와 접근성 (2026-11-26 같은 날 이어서 합의, 문서 반영 전)

- 조립마다 흐름도를 둘로 둔다: 원래 흐름도(마우스로 하는 것만)와 키보드 흐름도(키로 하는 것 전부, Esc와 입력 중 Enter 포함).
- 원칙: 꼭 있어야 하는 기능은 바탕 키(Tab, 방향키, Enter, Space, Esc)나 화면에 적혀 있는 키만으로 할 수 있어야 한다. 다른 방법으로 같은 결과를 낼 수 있으면 편의.
- 둘 수 있는 키는 바탕 키, 알려 줄 자리가 있는 키(툴팁·메뉴에 적힘), 어디서나 똑같이 쓰는 키(Ctrl+A, Shift+방향키)뿐. 이 블로그에서만 통하는 숨은 키는 만들지 않는다.
- 접근성 모드는 앱이다(바탕화면 아이콘은 지울 수 없음, 작업 표시줄 버튼은 지울 수 있음, Start·검색에도 나옴). 켜면 접근성 패널이 뜬다. 패널은 "우클릭을 대신 눌러 주는 단추"만 갖고 그 단추에 Shift+F10을 적어 알린다. Tab은 원래대로이고 패널이 끼어들지 않는다. 네 구석 가운데 자리를 고른다.
- 자리·순서 바꾸기는 메뉴의 이동 항목으로(Start 타일, 바탕화면 아이콘, 작업 표시줄 앱 버튼).
- 눌러도 아무 일이 없는 것(시계, 프로필 버튼)은 Hover를 빼고 포커스도 받지 않는다.

**How to apply (추가):** 단축키는 혼자 정하지 않는다. 문서·코드에 있는 것을 표로 가져가 조립 단위로 기능을 다 나열하고 하나씩 같이 정한다. Windows의 키라고 기억하는 것은 Microsoft 문서로 확인한 뒤 말한다(Ctrl+Space 선택 해제는 틀린 기억이었다). 사용자가 되물을 때는 내 안의 논리부터 다시 따진다(패널을 Tab 차례의 고정 자리에 두는 안은 대상이 바뀌어 성립하지 않았는데 사용자가 짚을 때까지 놓쳤다). 세부 기록은 세션 scratchpad의 `review/decisions.md`(지워질 수 있음).
