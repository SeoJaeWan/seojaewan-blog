# 개발 용어집

코드와 주석에서 만나는 개발 용어를 다시 찾아보기 위한 문서다. 영어 이름을 그대로 검색할 수 있도록 유지하고, 일반적인 뜻과 이 프로젝트에서의 쓰임을 구분한다. 주석은 기존처럼 한글 설명과 개발 용어·코드 식별자를 함께 사용한다.

이 문서는 현재 코드의 읽기 안내다. 상세 설계와 계약의 정본은 Workbench Local Work Memory의 `seojaewan/seojaewan-blog` 프로젝트에서 관리한다. 용어 설명과 구현을 함께 확인할 수 있도록 관련 소스 링크를 제공한다.

## Resource — 콘텐츠·폴더·외부 바로가기의 통칭

**일반적인 뜻:** 프로그램이 다루거나 사용하는 자원. 프로젝트마다 포함하는 대상이 달라진다.

**이 프로젝트에서는:** 아래 세 종류를 묶어 부르는 도메인 용어다. `ResourceKind`는 그 종류를 나타낸다.

| 타입               | `kind` 값           | 무엇인가                                                                     | 여는 방법                       |
| ------------------ | ------------------- | ---------------------------------------------------------------------------- | ------------------------------- |
| `Content`          | `content`           | 제목·요약 등의 정보를 가진 콘텐츠. 본문은 `ContentDocument`로 따로 조회한다. | 제품 안의 Chrome 탭에서 읽는다. |
| `Folder`           | `folder`            | 항목을 담고 탐색하는 폴더. 예를 들어 Blog·Project 같은 폴더다.               | 파일 탐색기 탭에서 탐색한다.    |
| `ExternalShortcut` | `external-shortcut` | 이름과 외부 URL을 가진 바로가기.                                             | 실제 브라우저의 새 탭으로 연다. |

**구분:** Chrome 앱 자체와 실행 중인 창은 Resource가 아니다. 폴더 원본에는 이름이 있지만, 부모 폴더와 바탕화면 배치 정보는 Workspace가 관리한다. `Content` 원본의 목록용 정보와 실제 본문도 구분한다.

**코드:** [Resource 모델](../packages/design/src/headless/resources/model/index.ts), [Resources 안내](../packages/design/src/headless/resources/README.md).

## ResourceRef · ResourceId · identity · UUID — 대상을 식별하는 값

**일반적인 뜻:** identity는 대상이 무엇인지 구분하는 정체성이고, ID는 이를 식별하는 값이다. ref는 reference의 줄임말로 다른 대상을 가리키는 참조다. UUID는 식별자를 표현하는 표준 형식이다.

**이 프로젝트에서는:** `ResourceId`는 UUID 형식의 식별자다. `ResourceRef`는 원본 전체 대신 `kind`와 `id`만 전달하는 값이며 세 종류가 있다.

| 참조 타입                     | 가리키는 대상      |
| ----------------------------- | ------------------ |
| `ContentResourceRef`          | 콘텐츠 하나        |
| `FolderResourceRef`           | 폴더 하나          |
| `ExternalShortcutResourceRef` | 외부 바로가기 하나 |

예를 들어 `{ kind: "folder", id: "57dd8487-031a-4f60-bc14-4f77f92be32f" }`는 특정 폴더를 가리킨다. 이름이나 부모 위치는 포함하지 않는다. 폴더 이름을 바꾸거나 이동해도 같은 ID로 가리킬 수 있다.

**구분:** 올바른 UUID 형식이라는 사실만으로 실제 항목이 존재한다는 보장은 없다. `ResourceRef`는 JavaScript 객체가 메모리에서 같은 객체인지 비교하는 object reference와도 구분해야 한다. 서로 다른 객체여도 같은 Resource를 가리킬 수 있다.

**코드:** [참조 모델과 검증](../packages/design/src/headless/resources/model/index.ts), [ID 형식](../packages/design/src/headless/resources/resourceId/index.ts).

<a id="catalog"></a>

## Catalog · Reader · Lookup · metadata — 원본과 정보 조회

**일반적인 뜻:** Catalog는 대상을 모아 둔 목록, Reader는 읽기 기능, Lookup은 식별자 등으로 대상을 찾거나 확인하는 동작이다. metadata는 제목·날짜처럼 대상을 설명하는 정보다.

**이 프로젝트에서는:** 종류별 Catalog에서 ID로 원본을 조회한다. `Content`의 제목·요약·태그, `ExternalShortcut`의 이름·URL 등이 원본 정보에 해당한다. `FolderCatalog`는 WorkspaceStore의 현재 폴더 목록을 읽는다.

`ResourceLookup.hasResource(ref)`는 해당 원본의 존재 여부만 알려준다. 제목이나 본문을 반환하지 않는다. `ContentDocumentReader`는 콘텐츠 정보와 본문을 읽는 별도 계약이다.

**예시:** 고정 목록에는 콘텐츠의 `ResourceRef`를 두고, 화면에 표시할 최신 제목은 Catalog에서 읽는다. 제목 변경 때 고정 목록의 복사본까지 수정할 필요가 없다.

**코드:** [Resources 조회 안내](../packages/design/src/headless/resources/README.md).

<a id="folder-file-explorer-chrome"></a>

## Folder · File Explorer · Chrome · Desktop — 탐색 대상과 앱의 차이

**일반적인 뜻:** Folder는 파일 등을 모아 두는 폴더이고, File Explorer는 Windows의 파일 탐색기 앱 이름이다. Chrome은 웹 브라우저 이름이고, Desktop은 바탕화면을 뜻한다.

**이 프로젝트에서는:** Windows와 브라우저에서 익숙한 이름을 빌려 블로그 안의 대상과 앱을 구분한다. 실제 컴퓨터의 폴더를 읽거나 설치된 파일 탐색기를 실행한다는 뜻은 아니다.

| 용어          | 역할                                   | 다루는 대상 또는 예시                         | 코드에서의 이름                                               |
| ------------- | -------------------------------------- | --------------------------------------------- | ------------------------------------------------------------- |
| Folder        | 탐색할 대상인 Resource                 | Blog, Project, Coding Test, About 같은 폴더   | `Folder`, `FolderResourceRef`, `kind: "folder"`               |
| File Explorer | 폴더와 그 안의 항목을 탐색하는 제품 앱 | 바탕화면 위치, Blog 폴더, 그 아래 폴더        | `applicationId: "file-explorer"`, `FileExplorerWindowSession` |
| Chrome        | 콘텐츠를 읽는 제품 앱                  | 새 탭 화면, 콘텐츠 본문, 내부 주소의 404 화면 | `applicationId: "chrome"`, `ChromeWindowSession`              |
| Desktop       | 제품의 바탕화면이자 탐색의 최상위 위치 | 어느 폴더에도 들어 있지 않은 항목이 놓인 위치 | `FileExplorerLocation`에서 `null`                             |

**Folder와 File Explorer:** Blog는 폴더의 이름이고, File Explorer는 Blog를 열어 보여 주는 앱이다. 여러 폴더를 열어도 앱 종류는 모두 File Explorer다. 탐색기 창을 닫아도 폴더 원본은 남아 있다. 코드의 `headless/folders` 디렉터리는 File Explorer의 탭 모델을 담고 있으므로, 디렉터리 이름만 보고 Folder와 앱을 같은 개념으로 해석하지 않는다.

**Content와 Chrome:** 콘텐츠는 읽을 대상이고, Chrome은 그 대상을 보여 주는 앱이다. 콘텐츠 하나가 Chrome 앱 하나를 의미하지 않는다. 데스크톱에서는 하나의 Chrome 창 안에서 여러 콘텐츠를 탭으로 읽을 수 있다.

Chrome 탭이 표시하는 위치는 다음 세 종류다.

| `ChromeLocation.kind` | 의미                                    |
| --------------------- | --------------------------------------- |
| `new-tab`             | 아직 특정 콘텐츠를 열지 않은 새 탭 화면 |
| `content`             | `ContentResourceRef`로 가리키는 콘텐츠  |
| `not-found`           | 찾을 수 없는 내부 주소의 404 화면       |

**제품 Chrome과 실제 브라우저:** 사용자가 Safari로 이 사이트에 접속해도 제품 안에서는 Chrome 앱을 열 수 있다. 제품 Chrome은 임의의 외부 사이트를 탐색하는 실제 브라우저가 아니다. 외부 바로가기를 열면 제품 Chrome 안이 아니라 사이트를 접속한 실제 브라우저의 새 탭으로 이동한다.

**Desktop과 탐색기 안의 Desktop 위치:** 창이 없는 바탕화면과, 파일 탐색기가 바탕화면 위치의 항목을 보여 주는 화면은 구분한다. 탐색기의 `null` 위치는 별도 이름이나 ID를 가진 Folder Resource가 아니다.

**예시:** 바탕화면의 Blog 폴더를 열면 File Explorer가 그 폴더의 항목을 보여 준다. 그 안의 글을 열면 Chrome이 글을 보여 준다. 글 옆의 외부 바로가기를 열면 실제 브라우저의 새 탭이 열린다.

**코드:** [Folder 원본 모델](../packages/design/src/headless/resources/model/index.ts), [File Explorer 위치와 탭](../packages/design/src/headless/folders/model/index.ts), [Chrome 위치와 탭](../packages/design/src/headless/chrome/model/index.ts), [Window 모델](../packages/design/src/headless/windows/model/index.ts).

<a id="windowsession"></a>

## application · WindowSession · tab — 앱, 실행 창, 창 안의 탭

**일반적인 뜻:** application은 앱, session은 일정 기간 유지되는 실행·사용 맥락이다. 여기서 session은 로그인 세션을 뜻하지 않는다.

**이 프로젝트에서는:** 앱의 종류는 `chrome`과 `file-explorer`이며, `WindowSession`은 그 앱으로 연 개별 창이다. 창 안에는 탭이 있다.

| 개념          | 현재 종류 또는 값                                  | 예시                                  |
| ------------- | -------------------------------------------------- | ------------------------------------- |
| application   | `chrome`, `file-explorer`                          | Chrome 앱                             |
| WindowSession | `ChromeWindowSession`, `FileExplorerWindowSession` | Chrome으로 연 첫 번째 창과 두 번째 창 |
| tab           | `ChromeTab`, `FileExplorerTab`                     | 첫 번째 Chrome 창 안의 콘텐츠 탭      |

제품 안의 Chrome은 이 블로그가 구현하는 앱 이름이다. 사이트를 접속한 실제 브라우저와 구분한다. 데스크톱에서는 창과 탭을 여러 개 열 수 있고, 모바일은 열린 창이 있다면 전체화면 창 하나와 그 안의 탭 하나만 유지한다.

**구분:** 같은 콘텐츠를 여러 창에서 열어도 `ResourceId`는 같고 `WindowSessionId`는 창마다 다르다. 창을 닫는 것은 콘텐츠 원본을 삭제하는 일이 아니다.

**코드:** [Window 모델](../packages/design/src/headless/windows/model/index.ts), [Window 사용 안내](../packages/design/src/headless/windows/README.md).

<a id="stackingorder"></a>

## stackingOrder · topmost · MRU · active · minimized — 창 순서와 상태

| 용어            | 일반적인 뜻                                    | 이 코드에서 읽는 방법                                                               |
| --------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| `stackingOrder` | 겹쳐 쌓인 순서                                 | 창 ID를 뒤쪽부터 앞쪽까지 저장한 배열. 마지막 항목이 순서상 가장 앞쪽이다.          |
| `topmost`       | 가장 위 또는 앞에 있는 대상                    | 창 겹침 순서의 가장 앞쪽을 뜻한다. 항상 위에 고정하는 별도 기능을 뜻하지 않는다.    |
| `MRU`           | Most Recently Used, 가장 최근 사용한 대상 우선 | 창을 새로 열거나 명시적으로 활성화할 때 배열 끝으로 옮기는 동작을 설명할 때 쓰인다. |
| `active`        | 현재 활성 상태                                 | `activeSessionId`가 가리키는 창. 각 창 안의 `activeTabId`와는 다른 상태다.          |
| `minimized`     | 최소화된 상태                                  | 창을 닫지 않고 화면에서 숨긴 상태. 창과 탭은 남아 있다.                             |

**예시:** 저장된 순서가 `[Chrome A, 파일 탐색기, Chrome B]`라면 앞쪽부터 읽을 때는 `[Chrome B, 파일 탐색기, Chrome A]`가 된다. 여기서 Chrome 창만 고르면 `[Chrome B, Chrome A]`다. `selectTargets`가 이 계산을 한다. 원본 배열을 직접 뒤집지 않고 복사한 배열을 뒤집는다.

**주의할 차이:** 현재 주석의 `topmost/MRU`를 완전히 같은 뜻으로 외우지 않는다. 이 구현은 별도의 사용 시간 기록을 정렬하지 않는다. 최소화할 때 기존 겹침 순서는 유지하며 다음 보이는 창을 활성화한다. 따라서 배열의 마지막 창이 지금 보이는 활성 창과 다를 수 있다. Taskbar 창 목록에는 최소화된 창도 포함된다.

**코드:** [Taskbar 창 목록 계산](../packages/design/src/headless/taskbar/selectors/index.ts), [창 활성화와 최소화](../packages/design/src/headless/windows/windowStore/index.ts).

<a id="pin"></a>

## Pin · Unpin · pinnedItems · visibleItems · running-only — 고정과 현재 표시

**일반적인 뜻:** Pin은 항목을 계속 보이도록 고정하는 동작, Unpin은 고정을 해제하는 동작이다.

**이 프로젝트에서는:** 시작 메뉴와 작업 표시줄이 서로 다른 고정 목록을 가진다.

| 목록                     | 포함하는 대상                                |
| ------------------------ | -------------------------------------------- |
| Start의 `pinnedItems`    | 콘텐츠·폴더·외부 바로가기의 `ResourceRef`    |
| Taskbar의 `pinnedItems`  | Chrome·파일 탐색기 앱과 외부 바로가기        |
| Taskbar의 `visibleItems` | 고정 항목과 실행 중이어서 표시되는 미고정 앱 |

`running-only`는 고정하지 않았지만 창이 열려 있어 작업 표시줄에 표시되는 앱을 뜻한다. 최소화된 창도 열린 창에 해당한다.

**예시:** Chrome 창이 열린 상태에서 고정을 해제하면 창은 닫히지 않고 작업 표시줄 항목도 남는다. 이후 마지막 Chrome 창을 닫으면 미고정 항목은 사라진다. 이 임시 표시 위치는 저장 대상이 아니다.

**코드:** [Start 모델](../packages/design/src/headless/start/model/index.ts), [Taskbar 모델](../packages/design/src/headless/taskbar/model/index.ts).

<a id="group"></a>

## Group · target · Preview — 앱별 창 묶음과 동작 대상

**일반적인 뜻:** Group은 묶음, target은 처리 대상, Preview는 미리보기다. target이 무엇인지는 사용하는 기능에 따라 달라진다.

**이 프로젝트의 Taskbar에서는:** Chrome 창들은 Chrome Group 하나로, 파일 탐색기 창들은 파일 탐색기 Group 하나로 묶는다. Group의 Window target은 개별 `WindowSession`이다. 미리보기 하나도 창 하나를 나타낸다.

**예시:** Chrome 창 두 개에 각각 탭 세 개가 있다면 Chrome Group의 창 대상은 두 개다. 여섯 탭을 여섯 개의 창 대상으로 세지 않는다. 외부 바로가기는 자체 실행 창을 만들지 않으므로 이 창 묶음에 속하지 않는다.

**코드:** [Taskbar selector](../packages/design/src/headless/taskbar/selectors/index.ts), [Taskbar 안내](../packages/design/src/headless/taskbar/README.md).

<a id="snapshot"></a>

## Store · state · snapshot — 상태 관리와 특정 시점의 상태 값

**일반적인 뜻:** state는 현재 상태, Store는 상태를 보관하고 변경을 관리하는 단위, snapshot은 특정 시점의 상태를 담은 값이다.

**이 프로젝트에서는:** `StartStore`, `TaskbarStore`, `WindowStore`, `WorkspaceStore`가 각자 맡은 상태와 명령을 제공한다. `getSnapshot()`으로 현재 반영된 상태를 읽는다.

**예시:** 고정 목록이 `[A, B]`일 때 읽은 snapshot과 C를 고정한 뒤의 `[A, B, C]` snapshot은 서로 다른 시점의 값이다. 앞서 받은 값에 C를 밀어 넣는 방식으로 갱신하지 않는다.

**구분:** snapshot이라는 이름만으로 저장소에 보관된 값이라는 뜻은 아니다. 현재 메모리 상태일 수도, 저장용 형식일 수도 있다. `getSnapshot()`을 호출할 때마다 새 복사본을 만드는 것도 아니다. 현재 Store는 이미 반영한 상태 객체를 반환한다.

**코드:** [StartStore](../packages/design/src/headless/start/startStore/index.ts), [TaskbarStore](../packages/design/src/headless/taskbar/taskbarStore/index.ts).

<a id="freezesnapshot"></a>

## immutable · readonly · freezeSnapshot — 직접 수정할 수 없는 상태 만들기

**일반적인 뜻:** immutable은 만들어진 값 자체를 변경하지 않는다는 뜻이다. TypeScript의 `readonly`는 타입 검사에서 직접 수정을 제한한다. `Object.freeze`는 JavaScript 실행 중에도 해당 객체의 속성 변경을 막는다.

**이 프로젝트에서는:** `freezeSnapshot`이 Start 또는 Taskbar 상태의 객체·배열·항목을 복사하고 동결한다. 외부 코드가 받은 목록을 직접 바꾸어 Store 명령을 우회하지 못하도록 한다. 변경이 필요하면 새 상태를 만들어 교체한다.

**예시:** UI가 현재 고정 목록을 읽었다고 해서 그 배열을 직접 수정하는 것은 허용되지 않는다. `pin`, `unpin`, `reorder` 명령으로 요청한다.

**구분:** `Object.freeze` 자체는 중첩 객체까지 자동으로 동결하지 않는다. 현재 두 helper는 자신이 다루는 내부 배열과 항목도 명시적으로 복사·동결한다. 어떤 종류의 객체든 처리하는 범용 깊은 동결 함수라는 뜻은 아니다. 입력 객체 자체를 동결하거나 저장하는 함수도 아니다.

**코드:** [Start의 freezeSnapshot](../packages/design/src/headless/start/startStore/index.ts), [Taskbar의 freezeSnapshot](../packages/design/src/headless/taskbar/taskbarStore/index.ts).

<a id="selector"></a>

## selector · derive · projection — 기존 값에서 필요한 정보 계산하기

**일반적인 뜻:** selector는 필요한 값을 고르거나 계산하는 함수다. derive는 기존 정보에서 결과를 도출하는 것, projection은 필요한 형태로 추려 변환하는 것을 뜻한다.

**이 프로젝트에서는:** Taskbar selector가 고정·표시 목록, 창 상태, 원본 정보를 조합해 화면에 필요한 값을 만든다. 예를 들어 앱별 창 목록과 현재 탭의 제목을 계산한다.

**구분:** 계산 결과를 별도의 원본 상태로 관리한다는 뜻은 아니다. `selectTargets`는 창을 열거나 창 순서를 변경하지 않는다. `toStorageSnapshot`의 projection은 저장에 필요한 값만 추리는 변환이다.

**코드:** [Taskbar selector](../packages/design/src/headless/taskbar/selectors/index.ts).

<a id="subscribe"></a>

## subscribe · listener · notify — 변경 구독과 알림

**일반적인 뜻:** subscribe는 알림을 받도록 등록하는 것, listener는 알림을 받을 함수, notify는 등록된 함수에 알리는 동작이다.

**이 프로젝트에서는:** Store의 `subscribe`로 상태 변경 알림을 등록한다. 반환된 함수로 구독을 해제할 수 있다. Store가 새 상태를 반영하면 등록된 함수가 현재 snapshot을 다시 읽을 수 있다.

**구분:** 상태 변경 알림은 저장 성공 알림이나 애니메이션 완료 알림이 아니다. Start와 Taskbar는 메모리 상태를 먼저 반영하고 알린 다음 저장할 수 있다.

**코드:** [StartStore의 subscribe와 notify](../packages/design/src/headless/start/startStore/index.ts).

<a id="mutation"></a>

## command · mutation · intent — 상태 변경 요청

**일반적인 뜻:** command는 실행할 명령, mutation은 상태 변경, intent는 수행하려는 의도를 뜻한다. mutation이 반드시 기존 객체를 직접 수정한다는 의미로 쓰이는 것은 아니다.

**이 프로젝트에서는:** `pin`, `unpin`, `reorder` 같은 Store 명령이 상태 변경의 진입점이다. 실제 배열을 직접 조작하는 대신 변경 의도를 전달한다.

**예시:** `reorder`에 `{ type: "index", index: 2 }`를 전달하면 항목을 최종 세 번째 위치로 옮기겠다는 뜻이다. 화면의 마우스 좌표가 아니라 목록의 최종 위치를 전달한다. index는 0부터 시작한다.

**구분:** 요청했다고 항상 상태가 바뀌는 것은 아니다. 검증 결과 거절되거나, 이미 원하는 상태라서 no-op이 될 수 있다.

**코드:** [StartReorderIntent](../packages/design/src/headless/start/model/index.ts), [TaskbarReorderIntent](../packages/design/src/headless/taskbar/model/index.ts).

<a id="commit"></a>

## commit · rollback — 상태 반영과 되돌리기

**일반적인 뜻:** commit은 작업 결과를 확정하는 것, rollback은 변경을 이전 상태로 되돌리는 것이다. 무엇을 확정하는지는 문맥에 따라 다르다.

**이 프로젝트의 Store에서는:** commit은 검증된 새 상태를 현재 메모리 상태로 반영하는 단계다. 구독자에게 변경을 알리는 처리도 이어진다. `semantic commit`은 이런 제품 상태의 의미 있는 변경을 가리키는 표현으로 사용된다.

**예시:** 콘텐츠를 시작 메뉴에 고정한 뒤 저장에 실패해도 메모리의 고정 목록에는 남아 있다. 결과의 `committed: true`는 상태가 반영됐다는 뜻이다. 저장 성공이라는 뜻은 아니다.

**구분:** Git 커밋, 저장소 쓰기 성공, 화면 애니메이션 완료를 의미하지 않는다. 현재 Pin 저장 실패 정책은 반영된 메모리 상태를 rollback하지 않는 것이다.

**코드:** [StartStore의 commit과 저장 실패 처리](../packages/design/src/headless/start/startStore/index.ts).

<a id="reconcile"></a>

## reconcile — 기준 상태와 대조하여 맞추기

**일반적인 뜻:** 서로 다른 정보나 상태를 대조해 차이를 정리하고 일치시키는 작업이다. 어떤 기준으로 무엇을 정리하는지 함께 읽어야 한다.

**이 프로젝트에서는:** 이름 뒤에 오는 대상에 따라 정리하는 내용이 다르다.

| 코드 표현                      | 기준과 동작                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| Start의 `reconcileResources`   | 현재 원본의 존재 여부를 확인해 삭제된 콘텐츠·폴더·외부 바로가기의 고정을 제거한다.    |
| Taskbar의 `reconcileResources` | 더 이상 존재하지 않는 외부 바로가기 항목을 정리한다.                                  |
| Taskbar의 `reconcileWindows`   | 현재 창 상태에 맞춰 작업 표시줄의 실행 중인 앱 표시를 갱신한다.                       |
| 내부 `reconcileVisibleItems`   | 남아 있는 항목의 위치를 유지하면서 사라질 항목을 제거하고 새 실행 앱을 끝에 추가한다. |

**예시:** 고정했던 폴더 원본이 삭제됐다면 시작 메뉴에 남은 해당 참조를 제거한다. 폴더 이름만 바뀐 경우에는 여전히 같은 폴더이므로 고정을 제거하지 않는다.

**구분:** 항상 저장소를 다시 읽는다는 뜻은 아니다. 다른 브라우저 탭과 실시간으로 동기화한다는 뜻도 아니다. React의 화면 갱신 문맥에서 사용하는 reconciliation과 처리 대상이 다르다.

**코드:** [StartStore](../packages/design/src/headless/start/startStore/index.ts), [TaskbarStore](../packages/design/src/headless/taskbar/taskbarStore/index.ts).

<a id="no-op"></a>

## no-op · rejected — 변경 없음과 요청 거절

**일반적인 뜻:** no-op은 no operation의 줄임말로, 수행해도 변경할 일이 없는 경우다. rejected는 요청을 받아들일 수 없어 거절한 경우다.

**이 프로젝트에서는:** 이미 고정한 항목을 다시 고정하는 요청은 no-op이다. 잘못된 이동 위치 같은 입력은 거절할 수 있다. 결과 타입의 구체적인 형태는 Store별로 다르다.

**구분:** no-op을 실패로 해석하지 않는다. 반대로 저장 실패는 상태가 이미 변경된 뒤 발생할 수 있으므로 no-op이나 변경 전 거절과 구분한다.

**코드:** [Start 결과 타입](../packages/design/src/headless/start/startStore/operationResult/index.ts), [Taskbar 결과 타입](../packages/design/src/headless/taskbar/taskbarStore/operationResult/index.ts), [Window 결과 타입](../packages/design/src/headless/windows/windowStore/operationResult/index.ts).

<a id="queue"></a>

## queue · atomic — 순서대로 처리하기와 하나의 변경으로 반영하기

**일반적인 뜻:** queue는 처리할 작업의 대기열이다. atomic은 중간 단계를 따로 노출하지 않고 하나의 단위로 다룬다는 뜻이다.

**이 프로젝트에서는:** Store가 초기화·변경·저장 작업을 순서대로 처리하도록 명령을 대기열에 넣는다. atomic reorder는 여러 번의 한 칸 이동을 외부에 알리는 대신 최종 위치로 옮긴 결과를 한 번의 상태 변경으로 반영한다.

**예시:** 저장이 느려도 후속 고정 변경은 앞선 작업 이후의 상태를 기준으로 처리한다. Taskbar는 창 변경 알림이 왔을 때 그 시점의 상태를 잡아 두고 나중에 순서대로 처리해, 그 사이의 닫기·재실행을 놓치지 않도록 한다.

**구분:** 여기서 atomic은 메모리 변경과 외부 저장이 반드시 함께 성공한다는 데이터베이스 트랜잭션 보장이 아니다.

**코드:** [Start 명령 처리](../packages/design/src/headless/start/startStore/index.ts), [Taskbar 명령과 창 변경 처리](../packages/design/src/headless/taskbar/taskbarStore/index.ts).

<a id="tostoragesnapshot"></a>

## toStorageSnapshot · schemaVersion · serialize — 저장할 형식 만들기

**일반적인 뜻:** storage snapshot은 저장할 상태 값이고, schema는 데이터의 구조다. schemaVersion은 그 구조의 버전이다. serialize는 데이터를 JSON 문자열처럼 전달·저장 가능한 표현으로 바꾸는 일이다.

**이 프로젝트에서는:** `toStorageSnapshot`이 메모리 상태에서 저장할 값만 골라 버전 정보와 함께 새 객체로 만든다.

| Store   | 현재 상태의 주요 필드         | 저장용 결과                                 |
| ------- | ----------------------------- | ------------------------------------------- |
| Start   | `pinnedItems`                 | `schemaVersion`, `resources`                |
| Taskbar | `pinnedItems`, `visibleItems` | `schemaVersion`, `items` — 고정 항목만 포함 |

**예시:** Taskbar에서 미고정 Chrome이 실행 중이면 `visibleItems`에 있지만 저장용 `items`에는 포함되지 않는다. 고정 항목의 제목이나 외부 URL도 이 저장값에 복사하지 않는다.

**구분:** 이 함수는 JSON 문자열을 만들거나 localStorage에 쓰지 않는다. 저장용 객체를 만드는 단계이며, 실제 저장은 `storage.save(...)`에 맡긴다. 저장용 결과도 외부에서 수정하지 못하도록 동결한다.

**코드:** [Start의 toStorageSnapshot](../packages/design/src/headless/start/startStore/index.ts), [Taskbar의 toStorageSnapshot](../packages/design/src/headless/taskbar/taskbarStore/index.ts).

<a id="persistence"></a>

## persistence · runtime · storage port · adapter — 실행 중 상태와 저장 경계

**일반적인 뜻:** persistence는 실행이 끝나도 데이터를 보존하는 영속성이다. runtime은 프로그램 실행 중인 시점이나 환경이다. port는 필요한 기능의 계약이고 adapter는 구체적인 환경에 맞춰 그 계약을 구현하는 연결부다.

**이 프로젝트에서는:** 창과 탭은 runtime 메모리에 둔다. 고정 목록은 저장 대상으로 다룬다. headless는 `load`와 `save` 형태의 storage port를 정의하고, Application에서 실제 저장 매체에 연결할 adapter를 제공한다.

**예시:** 브라우저의 localStorage를 사용하려면 Application이 그 읽기·쓰기를 구현해 Store에 연결한다. Store 모듈을 서버에서 import했다는 이유만으로 localStorage를 읽지는 않는다.

**구분:** 저장 계약이 있다는 것과 실제 브라우저 연결이 구현됐다는 것은 다르다. 현재 headless의 저장 처리는 주입받은 port를 호출하는 범위다.

**코드:** [Start 초기화와 저장 안내](../packages/design/src/headless/start/README.md), [Taskbar 초기화와 저장 안내](../packages/design/src/headless/taskbar/README.md).

<a id="restore"></a>

## seed · restore · reload · migration — 처음 값과 저장값 복원

| 용어        | 일반적인 뜻                       | 이 프로젝트의 예시                                               |
| ----------- | --------------------------------- | ---------------------------------------------------------------- |
| `seed`      | 초기 상태를 구성하는 기준 데이터  | Start의 빈 고정 목록, Taskbar의 파일 탐색기 → Chrome 고정 목록   |
| `restore`   | 저장된 값으로 상태를 복원         | 저장된 참조 중 유효하고 존재하는 항목을 복원                     |
| `reload`    | 데이터를 다시 읽기                | Store의 `reload()`로 저장소의 값을 다시 읽어 반영                |
| `migration` | 이전 데이터 구조를 새 구조로 변환 | 현재 Pin 구현은 이전 버전 저장값을 가져오는 변환을 제공하지 않음 |

**구분:** 저장값이 없는 경우와 정상적인 빈 목록은 다르다. 사용자가 모두 고정 해제해 저장한 빈 목록은 초기 고정 목록으로 다시 채우지 않는다. Store의 `reload()`와 실제 브라우저 페이지 새로고침도 서로 다른 호출이다.

**코드:** [Start 저장·복원 안내](../packages/design/src/headless/start/README.md), [Taskbar 저장·복원 안내](../packages/design/src/headless/taskbar/README.md).
